## Context

The repository is empty; motivation and scope are in `proposal.md`, behavior is in `specs/*/spec.md`. The technical foundation is the research doc `docs/research-code-canvas.md` (hereafter "the research"), accepted by the user as the plan with two amendments: spike G was added (text sharpness at fractional zoom), the benchmark runs only on the reference MacBook in a visible Chrome window.

Constraints shaping the design:
- Chrome on macOS, ProMotion 120 Hz; the criterion is DevTools Performance (spec `performance-budget`).
- The code is mostly written by AI agents. The architecture must be machine-checkable: module boundaries, size limits, and cycles are caught by the linter, not by review.
- The approach is DDD, a modular structure, **files no longer than 800 lines** (user's decision).
- Monaco is the only full-featured editor (user's decision); other libraries are allowed.

The domain vocabulary is `CONTEXT.md` at the repository root; the terms below are used in its meanings.

## Goals / Non-Goals

**Goals:**
- A modular monolith of bounded contexts with explicit, linter-checked dependencies.
- A hot frame path (pan/zoom/drag) with no per-widget/per-glyph allocations and no waiting on workers.
- An architecture where every risky assumption from the research is closed by a spike before main development.
- A set of linters and gates that an agent runs with a single command.

**Non-Goals:**
- Multi-user support, a backend, deployment.
- Languages other than TypeScript/TSX; line wrapping. Wide characters (CJK, emoji) are drawn with the advance the browser's text engine gives them (≈1.7 narrow advances from the fallback font, not 2 — spike C, confirmed 2026-09-29), the same advance Monaco's DOM uses, so they stay aligned with the editor. Emoji are drawn as Canvas2D draws them — in colour, as in Monaco's DOM; colour emoji are not a requirement (user's decision, 2026-10-01).
- Font ligatures and right-to-left text: the tile raster draws one grapheme cluster at a time at LineLayout's x (D4, D6) and does not shape runs, so the GPU view keeps one arithmetic layout (VS Code's GPU renderer and xterm.js's WebGL renderer have the same limit). Ligatures are off in the editor too, so both views show the same glyphs.
- Support for browsers other than Chrome; WebGPU.
- A UI framework (React, etc.): the UI outside the canvas — a handful of panels — is written with the DOM API.

## Decisions

### D1. Modular monolith, bounded contexts

A single application (Vite + TypeScript, one `package.json`), with the code split into contexts. A monorepo with packages was rejected: for a single application it means extra build configs with no payoff, and boundaries are already checked by the linter (D10).

| Context | Type | Responsibility | Main concepts |
|---|---|---|---|
| `workspace` | core | the folder on disk, files, revisions, writing, conflicts | WorkspaceFolder, SourceFile, FilePath, FileRevision, SaveConflict |
| `board` | core | the spatial model of the canvas | Board, Widget, WidgetFrame, StackOrder, ContentScroll, Camera, DetailLevel, GridLayout |
| `code-view` | core | how code looks and gets to the GPU: tokens, palette, line layout, document residency | TokenizedDocument, TokenRun, ThemePalette, LineLayout, DocumentResidency |
| `editing` | core | the editing lifecycle of a single widget | EditingSession, Draft, AutosavePolicy, EditingTransition |
| `rendering` | generic (technical) | GPU mechanics: context, Text Tiles and their raster workers, passes; the generic frame-stage runner | TilePool, WidgetTable, GpuUploader adapter, RenderPass, FrameLoop |
| `interaction` | supporting | translating raw input into per-frame intents and context commands | GestureTargeting, Shortcut |
| `performance` | supporting | frame metrics, overlay | FrameStats |
| `app` | composition root | wiring dependencies, screens outside the canvas | — |

`rendering`, `interaction`, and `performance` have no domain layer: they are technical modules and don't need the DDD hierarchy.

### D2. Context map

```
                      low-frequency domain events (bus)
 workspace ──FilesDiscovered(folderId, files)──▶ board (restoreBoard → reconcile)
 workspace ──FileContentChanged(fileId, version, text, lines)──▶ board (content height)
                                                └──────────────▶ code-view (DocumentResidency)
     ▲
     │ readForEditing / applyDraft (application services)
  editing (EditingTransition) ◀── commands ── interaction (GestureTargeting) ── commands ──▶ board

                      per-frame pulls (Frame Stages declared by app, run by FrameLoop, no events)
 app ──stage list──▶ FrameLoop ──runs──▶ interaction, board, rendering, code-view, editing stages
 FrameLoop ──Frame Sample (shared/frame)──▶ performance (FrameStats, overlay)
```

- **workspace → board**: `FilesDiscovered(folderId, files)` (each file: `SourceFileId` + line count) → board's infrastructure loads the saved layout for `folderId` and hands it to the application-layer `restoreBoard`, which reconciles it with the discovered files in one step (D12). Board references files only by `SourceFileId` and folders only by `WorkspaceFolderId`; it never sees file-system handles. A `SourceFileId` is the file's File Path relative to the folder.
- **workspace → board, code-view**: `FileContentChanged(fileId, contentVersion, text, lineCount)` on every new Content Version — a read from disk or an applied Draft. This is the only path by which text reaches `code-view`: `DocumentResidency` takes the text; board updates the widget's content height and re-clamps its Content Scroll.
- **Content Version vs File Revision**: Content Version is an in-memory counter per Source File, bumped synchronously on every text change; it keys tokenization and GPU data. File Revision is the content hash of what is on disk; it guards writes against conflicts (D12). Keeping them apart lets a Draft reach the screen in the same frame while the hash and the write stay asynchronous.
- **editing ↔ workspace**: editing calls workspace's application services `readForEditing` (with conflict detection) and `applyDraft(fileId, text)`. `applyDraft` synchronously bumps the Content Version and emits `FileContentChanged`, then schedules the asynchronous write. Conflict is a workspace concept. The write's outcome is published as `DraftWritten(fileId, contentVersion)`, `DraftWriteFailed(fileId)` or `SaveConflictDetected(fileId)`; the last is also published by a `readForEditing` that finds a conflict, so no conflict is silent (D12).
- **Exiting with edits**: the `EditingTransition` module (D9) applies the Draft, marks the file as a priority in `DocumentResidency`, and hands the FrameLoop one swap record. The FrameLoop applies it in the first tick in which the widget's visible Text Tiles are current for the new Content Version or a newer one (single colour allowed, D6) — a reread during the hold, such as a conflict resolved to the disk version, supersedes the awaited version, and requiring equality held Monaco forever; until then Monaco stays visible and stationary but read-only — a keystroke after the Draft was taken would be lost — no new Editing Session can begin, and the gesture that ended the session keeps accumulating as the pending gesture — the camera does not move. In that tick Monaco is hidden, the tiles are shown and the pending gesture replays, so no frame shows the old content (spec `code-editing` "Exiting editing"); highlighting arrives from the worker within 100 ms. The hold is bounded by one widget's visible tiles in the raster workers. Spike H2's per-tile medians (raster ≈1 ms at zoom 1, transfer and upload ≈4 ms) suggested 1–2 frames; measured 2026-10-02 in headed Chrome at 120 Hz (e2e "Highlighting after an edit", machine load ~6.5) it is 35–55 ms (4–7 frames) for a one-line file and 45–51 ms for a 2000-line file. Its floor is the raster round trip — jobs posted in one tick's drain, tiles uploaded in a later drain, the swap on the tick after, because this stage runs before the drain — plus the widget's several tiles on two workers. When the new version's tokens land during the hold (a small file now; every edit once task 8.3's incremental Tokenizer lands), the content epoch changes and the tiles are rasterized once more, which keeps the exit frame highlighted. Counting a tile of any epoch as current for the Content Version was rejected (user's decision, 2026-10-02): it saves about two frames only when tokens land mid-hold, shows the text without highlighting for 1–2 frames after the exit, and does nothing for large files. The tiles are to be current before the exit instead: each autosave publishes the Draft as a Content Version (task 11.2) and the widget's tiles are rasterized under Monaco, so an exit after a pause in typing swaps in its first tick. The harness measures the hold (task 11.8). If the raster workers fail — the start-up font check or a worker error — rendering enters its error state (D6 "Raster workers": text is not drawn, the error is shown) and the hold is released; there is no timeout, because a timed release could show the old content (user's decision, 2026-10-02). An exit without edits waits for the same coverage at the Content Scroll handed back from Monaco (D9); when the view did not move its tiles are already resident and it swaps in its first tick. Rejected (user's decision, 2026-10-01): keeping Monaco until the *tokens* are ready (ties the hold to tokenization, up to 100 ms), and rasterizing the widget on the main thread in the swap tick (main-thread tiles alone reached 6.2 ms JS p99 in H2).
- **interaction → board/editing**: only application-layer commands, produced from per-frame intents of `GestureTargeting` (D8); no direct mutation of domain objects.
- **Per-frame work**: each context exposes its Frame Stage through its public `index.ts`; `app` wires the D8 order into the FrameLoop. `rendering` contributes only the cull and draw stages and receives the projections it draws (WidgetTable rows, Camera, Detail Level) from `app`'s wiring; of the core contexts it reads only `Camera`/`CameraView` from `board` and `LineLayout`/`LineNumberGutter` from `code-view`, through their `index.ts` (D5; user's decision, 2026-10-06, after the architecture review found the earlier "imports no core context" no longer true). No stage subscribes to domain events or writes to another context's domain.

The event bus is synchronous, in-process, and typed (`shared/events`), and carries only low-frequency events between contexts (folder opened, content changed, editing started/ended). Per-frame state is pulled, never pushed through the bus. Asynchrony exists only at infrastructure boundaries (the tokenization worker, File System Access, IndexedDB).

### D3. Layers inside a core context

```
<context>/
  domain/          pure TS: entities, value objects, aggregates, domain events, policies. No DOM, WebGL, Monaco, async I/O.
  application/     use cases (commands/queries), ports (interfaces) to infrastructure, subscribers to other contexts' events.
  infrastructure/  port adapters: File System Access, IndexedDB, Web Worker, Monaco.
  index.ts         the context's public API: commands, read model, event types. The only entry point from outside.
```

Dependency rules (checked by the linter, D10):
- `domain` → only `shared/domain`, `shared/geometry`.
- `application` → its own `domain`, `shared`, other contexts' public `index.ts`.
- `infrastructure` → its own `application`/`domain`, `shared`, external libraries.
- Importing another context is only through its `index.ts`; deep imports are forbidden.
- Any context's infrastructure is imported only by `app` (composition root).
- `monaco-editor` — only in `editing/infrastructure` and `code-view/infrastructure`; `twgl.js` and WebGL — only in `rendering`.
- Cycles between modules are forbidden.
- Only core contexts have a public `index.ts` entry that other modules may import. Technical modules (`rendering`, `interaction`, `performance`) may import core contexts' `index.ts` (e.g. `rendering` implements code-view's `GpuUploader` port, `interaction` calls Board's hit-test), but no module imports a technical module except `app`; `performance` reaches frame data only through the Frame Sample type in `shared/frame`, and `perf/` only through `performance/bridge.ts`. Technical modules take the widget id type from Board's public types, never from `shared/domain`, which the map does not open to them.
- These rules are declared once, as a **Module Map** table (modules, layers, public entries, allowed edges, where each library may be used), from which the lint rules and knip entries are generated; a matrix test over real `src/` paths checks every allowed and forbidden edge (D10).

### D4. Aggregates and invariants

- **Board** (the root) with **Widget** entities. Invariants: one widget per `SourceFileId`; `WidgetFrame` is never smaller than the minimum; `StackOrder` is a strict order with no duplicates; `ContentScroll` stays within `[0, contentHeight − viewportHeight]`, recomputed on resize and whenever the line count changes. **Camera** is a value object inside Board: scale in `[0.05, 4.0]`, zooming toward a point keeps that point under the cursor. `GridLayout` is the domain policy for the initial layout; `reconcile(savedLayout, discoveredFiles)` is a pure policy that keeps saved widgets, drops missing files, and places new files to the right of the grid. Fit all fits the widgets' bounding box with a 40 screen px margin on each side, centred, within the Camera's scale bounds; on an empty board the camera does not move. Zoom to 100% zooms about the viewport centre. A double click on a widget at Minimap zooms to it at scale 1: centred on each axis where it fits with 40 px margins, otherwise with its left or top edge at 40 px.
- **DetailLevel** lives in Board next to Camera. The on-screen line height (`lineHeight × zoom × DPR`) is the same for every widget, so there is one Detail Level per Camera, not per widget. Board stores the current level and applies hysteresis (different thresholds for zooming out and zooming in) whenever the Camera changes; a switch to Text also waits until the visible widgets' Text Tiles are resident, an input the frame passes in (D6 "Detail Level transition"). Board also answers whether Text is wanted — the level is Minimap but the line height is already above the zoom-in threshold — so rendering requests the visible tiles even when the camera reached a Text zoom without a gesture (a harness camera jump, Fit all, a double click on a Minimap); otherwise the switch would wait for tiles nobody requests. The base line height is configuration given at composition from `code-view`'s LineLayout. `rendering`, `interaction` and the metrics overlay only read it. Numeric thresholds are set after spikes E/G.
- **Hit-test** is a pure query on Board: top-most widget under a screen point, then the zone (header, edge, body, empty canvas); for the body it returns a body-local point in content coordinates (Content Scroll applied). It uses the same Widget Frames, Stack Order and Camera as rendering. The resize grab bands lie just outside the frame's right and bottom edges and corner and are 8 screen px wide at every zoom (8 / scale board px). At Minimap the whole frame counts as header, so a widget can be dragged from anywhere at far zoom. Turning that point into a line and column is LineLayout's job, so Board's domain holds no text rules.
- **LineLayout** (`code-view/domain`, pure) is the single owner of "text → rows and x positions":
  - **Line splitting matches Monaco's text model** (user's decision, 2026-09-29): breaks are LF, CRLF and CR; a leading BOM is not a character; the empty file is one empty line; a trailing line break produces a final empty line (a 2000-line file ending in `\n` has 2001 lines, the last one empty). Monaco is the reference the GPU view swaps with, so line numbers and Content Scroll agree by construction.
  - Iteration is by **grapheme cluster** (`Intl.Segmenter`, granularity `grapheme`, as VS Code's GPU renderer does): the browser draws a cluster — a ZWJ emoji sequence, a base letter with combining marks, a flag, an emoji with a variation selector — as one glyph with one advance, so summing its code points' advances is wrong (the Text Metrics conformance test measured a 40 px shift after one ZWJ sequence, 2026-09-29). Surrogate pairs are inside clusters (`charAt` splits them, spike E). One cluster = one `fillText` in the tile raster and one Text Metrics advance; UTF-16 offsets still address columns for Monaco and tokens. Tab stops follow Monaco's DOM renderer (not its experimental WebGPU one): visible columns are counted per UTF-16 code unit, a code unit Monaco treats as full-width counts 2, and a tab advances `tabSize − column % tabSize` narrow advances — so an emoji before a tab counts two columns. A line whose code units are all below 0x80 skips `Intl.Segmenter` (one object per cluster) with identical output: the line-window build of the prioritized widget was ≈60% of the editing-exit tick.
  - **Advances are fractional, per code point** (spike C): a glyph's x is the prefix sum of the advances before it. Integer cells are not enough: CJK and emoji are ≈1.7 narrow advances wide. LineLayout does not measure anything; it receives **Text Metrics** (narrow advance, `advanceFor(codePoint)`, baseline, line height) as configuration at composition. Where Text Metrics come from is D6 "Text Metrics".
  - UTF-16 offset ↔ x position conversion, the hit-test column, the worker's token offsets, the GpuUploader line windows, workspace's line count and Monaco's options (`tabSize`, end of line, `fontSize`/`lineHeight`) all derive from it; the line-splitting rule itself lives in `shared/domain` so workspace can count lines without importing code-view. The Reference Dataset generator uses the same rule (`fixtures/lib/dataset.ts` `splitSourceLines` is its reference implementation until `shared/domain` exists), and the Edge-case Corpus `expected` records are LineLayout's test table.
  - Five splitting rules existed before this decision (fixtures, spikes C/E, spike D2's worker, `check-max-lines`, Monaco); spike D2's worker split on `\n` only, leaving `\r` in line text and shifting token offsets. Product code never splits lines itself.
- **WorkspaceFolder** (identified by `WorkspaceFolderId`) with **SourceFile** entities (path, Content Version, File Revision = hash of the on-disk content; `lastModified` and size are only a quick change indicator). Invariants: a file filter (`.ts/.tsx`, directory exclusions); a write is allowed only from a known File Revision, otherwise — `SaveConflict`.
- **EditingSession**: states `Idle | Editing(widgetId, draft, dirty)`; at most one active session — an aggregate invariant, not a UI convention. The editor placement (Camera and Widget Frame) is copied when the session begins, which keeps the editor stationary. `end()` refuses unpublished edits — the caller publishes the Draft first; `discard()` ends a session without saving (the "keep the version on disk" answer to a Save Conflict). `AutosavePolicy` — due 1 s after the last edit, and on exit.
- **TokenizedDocument** (`code-view`): immutable, tied to `(fileId, contentVersion)`; stores lines as packed `Uint32Array` token runs (offset + palette color index), as in Monaco.

### D5. Hot path: DDD does not participate in per-frame work

Tension: DDD objects with invariants are convenient for commands, but the 120 Hz hot loop must not go through them for every widget. The solution is **CQRS-lite**:
- Commands (pan, drag, resize, scroll) go through the application layer and the domain with primitive arguments: O(1) work per input intent, no event objects.
- Board records which widgets changed in a dirty set. Once per frame, at the camera stage, `rendering` drains the dirty ids and copies those widgets into its own projection in typed arrays (`WidgetTable`: position, size, scroll, depth) — one table row per changed widget. Update ordering is therefore the FrameLoop's tick order (D8), not event delivery order. `restoreBoard` replaces the whole widget set: it bumps Board's `layoutVersion` and marks every widget dirty, and a projection rebuilds itself when it sees a new `layoutVersion` (an O(1) poll).
- A frame reads only the projections, the Camera and the Detail Level. Rule for `rendering/` and `interaction/`: per-frame code has no per-widget/per-glyph allocations (a review checklist + the harness catches GC pauses).

Rejected: "rendering reads domain objects directly" — couples the domain to the GPU data format and invites allocations in the loop; "rendering subscribes to hot-path domain events" — every pan or drag would pass command → domain → bus → subscriber, with reused event objects that a subscriber can accidentally retain and an unwritten ordering between bus delivery and the tick.

### D6. Rendering (WebGL2)

- **A single WebGL2 context** for the whole application, on the main thread (research, items 2/5). Moving the scene to OffscreenCanvas in a worker was rejected: swapping the GPU representation for Monaco and back must happen within a single frame together with the DOM, and cross-thread synchronization via `postMessage` doesn't guarantee that. Text Tiles are *rasterized* in workers (below), but composited by this context. The camera is stationary while editing (spec `code-editing` "Stationary editor"), so there's no need for frame-by-frame synchronization of Monaco with panning.
- **Raw WebGL2 + twgl.js** (research, Tradeoff Matrix). Fallback path — PixiJS v8 with a custom Mesh, if spike B shows that a homegrown renderer won't fit the schedule.
- **Text Tiles** (spike H2, user's decision 2026-10-01): a widget's body — line numbers and code — is drawn from square RGBA images of 512 × 512 device px. A tile covers a fixed square of the widget's *content* at one raster scale (camera zoom × DPR): tile (column, row) covers content x ∈ [column·s, (column + 1)·s) and y ∈ [row·s, (row + 1)·s), with s = 512 / rasterScale CSS px (256 CSS px at zoom 1, DPR 2). Tiles are anchored to content coordinates: pan, drag and resize only move or clip them (Camera and the widget's `WidgetTable` row, a data texture the shader reads), and in-widget scroll shifts them by the Content Scroll in the shader — a sub-tile offset plus one extra row at the edge, with no raster until a new row enters (H2 scrolled in whole tile rows; smooth scroll is measured by the harness). Rejected: the glyph atlas — its per-frame cost grows with the visible glyphs (H2 on 80-line files: density JS p99 16 ms, GPU p99 11.5 ms) and it crashed the renderer on full-size files; tiles rasterized on the main thread (JS p99 up to 6.2 ms). Spike G's discrete atlas sizes applied to the atlas and no longer apply.
- **Raster workers**: a small pool of module workers, separate from the Tokenizer pool so a tokenization chunk (~18 ms) never delays a visible tile (size calibrated by the harness; 2 to start), rasterizes tiles with `OffscreenCanvas` 2D: the widget background, then one `fillText` per grapheme cluster at LineLayout's x and the Text Metrics baseline with its palette colour (spike H's `drawRasterCells`); tabs are expanded per LineLayout, ligatures are disabled. Each worker draws with the one font definition in `shared/font.ts`, which also configures Monaco — today the system Menlo the Text Metrics were measured with (a font file, if one is ever bundled, is loaded through `FontFace` in each worker); at start-up its `measureText` of the probe character must equal Text Metrics' narrow advance, or the app stops with an error instead of drawing with a fallback font. A worker that fails later (its `error` event) is treated the same way: text is not drawn and the error is shown, and a held editing exit is released (D2). A job carries the tile key and its lines' cells as transferable typed arrays (code points, x offsets, colour indexes); the result is a transferable `ImageBitmap`; a tile whose Content Version or raster scale is no longer wanted when it arrives is closed (`ImageBitmap.close()`), never uploaded. The main thread only uploads (`texSubImage2D` from the bitmap — ≈0 ms of main-thread time per tile in H2) and composites. Building a job is main-thread work: its cells are written straight into the job's typed arrays (no string or object per glyph), and jobs are posted under a 2 ms time budget per frame, at least one and at most four per frame — four jobs per frame with no time budget let the tick that ends an editing session overrun. Raster jobs for visible widgets go out top-most first. Measured per tile in H2 (worker): raster median 0.8–1.0 ms at zoom 1 and 6.1–6.4 ms at the density zoom 0.225, where one tile holds a whole widget body.
- **Tile pool**: fixed RGBA slots in GPU texture memory, allocated outside the frame and never re-created inside one (H2: one 3072² px texture, 36 slots, 36 MiB — enough for its 1200 × 720 CSS-px view). The pool is one `TEXTURE_2D` atlas: tiles are uploaded with `texSubImage2D` at integer texel origins, `MAX_TEXTURE_SIZE` is checked at construction, and the tile shader clamps its UVs to the slot ± half a texel, so sampling never bleeds between slots. A `TEXTURE_2D_ARRAY` was rejected: in this Chrome (ANGLE Metal) uploading a worker's `ImageBitmap` with `texSubImage3D` measured 2.6 ms median (p90 4.0, max 5.3) against ≈0 ms (p90 0.1) for `texSubImage2D`; typed-array uploads into an array are fast. At rest, a tile quad sits on whole device pixels (its screen translation is rounded), so its texels map 1:1 to the screen; a sub-pixel offset would blur the text through `LINEAR` filtering. The pool holds the visible tiles of every visible widget, a one-tile margin ring and the old-scale tiles kept while a zoom settles; it starts at 128 full slots plus 32 slots cut into 512 × 32 device-px cells (16 per slot, with their own LRU), so a header or label tile at most 31 device px tall takes a cell, not a full slot (160 MiB in all). The pool grows outside the frame when the pinned tiles plus the missing ones do not fit: a per-frame check, run only while tiles are missing, schedules a growth by ×1.25 in whole atlas rows from a timer, and the new texture receives the old rows with `copyTexSubImage2D`. It never shrinks and is capped at 480 tiles (~0.5 GiB). Without growth the maximized density view at DPR 2 never settled: fallback tiles stay pinned until the visible text is exact, so the exact tiles evicted each other forever. Slots are reused least-recently-used; visible and fallback tiles are never evicted. Uploads never set `UNPACK_FLIP_Y_WEBGL` (the flip lives in the tile UVs). Tile memory and missing-tile frames go into the Frame Sample.
- **Tiles per widget**: each widget has its own tile records, planner and content epoch; the pool, the raster job queue, the tile pass and its painter are shared, and tile keys include the file id. Readiness for the switch to Text waits for every visible widget whose file has content; an undecodable file never blocks it. The settled zoom and time to sharp are camera-wide.
- **Widget chrome and opaque tiles**: the frame is 1 device px; a 12 board-px gutter is reserved at the body's right edge at all times (like Monaco's scrollbar column), and the scroll thumb is drawn in it at Text when the content does not fit — height `max(20, body² / content)`, top `bodyTop + (body − thumb) × scroll / maxScroll`. Chrome colours are VS Code Dark+ constants in one rendering module, not read from the theme. Text tiles are opaque (the raster fills the tile), so every tile is rasterized on the colour of the region it covers and clipped to that region's interior: body tiles inside the frame and left of the gutter, header tiles inside the frame; minimap quads are clipped to the frame. Label tiles stay transparent. A new tile kind follows the same rule.
- **Zoom**: a tile is sharp at its raster scale and scaled by the GPU (`LINEAR`, no mipmaps) at any other. During a zoom gesture visible tiles are re-rasterized in steps (user's decision, 2026-10-04): a visible cell requests a tile at the **gesture step scale** — the step of the √2 ladder `2^(k/2) × DPR` nearest to zoom × DPR (ties to the larger) — unless ready tiles of the current epoch whose scale is within √2 of zoom × DPR cover it; until the new tile arrives the old one is drawn scaled. The visible text is then never more than about 1.19× off its raster scale for long, instead of being stretched for the whole gesture (before: blurry until release). It follows the Chrome compositor, which also rasterizes new tilings while a pinch is in progress; text drawn from distance fields (SDF, MSDF, Slug) was rejected — no hinting at code sizes, per-glyph frame cost like the atlas H2 rejected, and no match with Monaco's DOM at the editing swap. Stage mode measured no main-thread cost (zoom worst task 3.61 → 2.55 ms, density 4.35 → 3.20 ms, tile memory and missing-tile frames unchanged). Widgets the gesture is about to reveal — those in the view at the next power-of-two zoom step around the focus point — get tiles during the gesture at a coarse scale (the largest power of two not above the current zoom), so a widget entering the view usually has text in its first frame; a frame where a visible widget has no resident tile counts as a missing-tile frame (H2: 1–2 per run). When GestureTargeting reports the gesture's end (it owns gesture boundaries, the momentum phase included; rendering keeps no settle timer of its own), the visible tiles are re-rasterized at the exact settled scale; the old tiles stay on screen, scaled, until every visible replacement is resident (H2), so no frame is empty. The exact scale and the same font engine as Monaco's DOM — which also rasterizes at its final scale under the CSS transform (D9) — make the frames before and after an editing swap match. Time to sharp runs from the end of a zoom gesture that ends at Text to the frame in which every visible widget with text has its exact-scale tiles resident; the next zoom gesture restarts it, a switch to Minimap cancels it, and a camera change without a gesture (a harness camera jump, Fit all, a double click on a Minimap) never starts it. It was not measured in H2; from the per-tile costs it is estimated at tens of ms at zoom 1 and ~0.1–0.2 s at the density zoom with two workers; the harness measures it.
- **Draw and request sets** (user's decision, 2026-10-02, after round R1 of the tiles slice drew empty frames after every zoom settle and every token delivery): a tile's identity includes an epoch bumped by every content change (a new Content Version or new tokens), and a content change releases nothing. Each frame the uploader builds two sets with one coverage rule (a cell clipped to the content and the view counts as covered when its four corners and centre lie inside resident tiles):
  - The **request set** uses one scale rule at every Detail Level: the exact raster scale at rest; during a zoom gesture the gesture step scale for visible content (a cell covered only by tiles more than √2 off zoom × DPR is requested), headers and labels, and the coarse scale (largest power of two not above the zoom, × DPR) for the widgets the gesture is about to reveal, where covered cells request nothing. Headers and labels took the coarse scale until 2026-10-07: stretched up to 2×, the file path looked blurry during a zoom (user's decision, 2026-10-07; perf:stages Zoom app task 2.40 → 2.10 ms, within noise). The draw set picks among resident records of every kind by the same rule: at rest the at-rest scale first, then the larger scale; during a zoom gesture the scale closest to zoom × DPR, then the larger. Requesting step-scale headers alone changed nothing on screen, because the draw set still preferred the at-rest header, stretched without limit. One module (`text-tile-raster-scale-rule.ts`) owns both rules per tile kind — the request scale and the better record — and the planner, the draw set, the tile lifecycle and the debug snapshot ask it; header columns come from the header's own tile size (user's decision, 2026-10-07, after an architecture review). At Minimap only header tiles and the zoom-in prefetch are requested, unless Board says Text is wanted (D4).
  - The **draw set** is the minimal set of resident tiles that covers the view with the best available quality: a newer epoch first, then the at-rest exact scale, then a higher raster scale; during a zoom gesture content tiles rank by epoch and then by how close their raster scale is to zoom × DPR. A worse tile is drawn, underneath, only where better tiles leave a gap — so the old text never shows where the new text is resident (D2).
  - A raster result is uploaded only if its tile is still in some request list of the frame; otherwise it is closed and its record released.
- **Text Metrics** (`rendering/text`, decided 2026-09-29 after 3.2's alignment failures and a research pass on VS Code's GPU editor renderer): one module measures the font with the **browser's text engine** and is the only source of horizontal advances and the baseline for the GPU view; Monaco is configured from the same font definition and is not a source of metrics. In Chrome, Canvas2D `measureText` and DOM layout use the same `blink::Font`/HarfBuzz shaping (measured 2026-09-29: identical advances to 0.001 px for ASCII, Cyrillic, CJK fallback and emoji at 16 px Menlo).
  - Inputs: the one font definition in `shared/font.ts` (family, size, line height, tab size, `font-feature-settings` with ligatures off, `letter-spacing` 0) — the same object configures Monaco.
  - Narrow advance: a laid-out, hidden DOM `<span>` of the probe character repeated 256 times, `width / 256` (VS Code `charWidthReader`); per-code-point advances: Canvas2D `measureText` with `fontKerning`, `letterSpacing` and feature settings mirrored from the DOM style, cached per code point, measured lazily on the main thread outside the frame (through the drain budget); the raster workers receive x positions and never measure.
  - Baseline: CSS half-leading from one `measureText` per font and size — `floor((lineHeight − (fontBoundingBoxAscent + fontBoundingBoxDescent)) / 2) + fontBoundingBoxAscent` (VS Code `fullFileRenderStrategy`); measured 15 px for 16/20 Menlo, equal to Monaco's DOM.
  - One rounding rule, applied here and nowhere else (xterm.js's WebGL and DOM renderers diverge because each floors the shared width differently).
  - Monaco options that keep its DOM on the same metrics: ligatures off, `letterSpacing` 0, line numbers as in "Line numbers" below, no glyph margin, folding or indent guides, `renderLineHighlight: "none"`, background from the one theme object. `disableMonospaceOptimizations: true`: with Monaco's monospace fast path its ASCII advance measured 9.641 vs the engine's 9.633 (≈1 px per 120 columns); with the option on, Monaco positions glyphs by DOM layout and the conformance test measured max |Δx| ≤ 0.04 CSS px and baseline Δ 0 on the Edge-case Corpus at zoom 1 and a snapped zoom (2026-09-29). Turning the fast path back on for speed was measured on 2026-10-03 and rejected: the frame after a large edit did not shrink, because Monaco's forced layout only moved into the frame's own layout phase.
  - **Line numbers** (user's decision 2026-10-04): the line-number gutter is one geometry used by both views. The number area is `round(max(4, digits(lineCount)) × digit advance)` wide — Monaco's own layout formula for `lineNumbersMinChars` — numbers are right-aligned in it, and code starts after it plus a fixed gap equal to Monaco's `lineDecorationsWidth`. The tile raster draws the numbers in this gutter; while editing, Monaco draws them (`lineNumbers: "on"`, `lineNumbersMinChars` and `lineDecorationsWidth` from the same constants, colour from the one theme object), so numbers follow edits and scroll live and nothing moves on the swap. A click on the body maps to a column after subtracting the gutter. The conformance test measures code x including the gutter. Rejected: keeping the gutter on the GPU view while editing (spike, 2026-10-04) — numbers would update only on line-count changes, each such edit republishes the whole file, and the gutter must follow Monaco's scroll every frame; `perf:stages` could not tell the two apart.
  - Verification is a **conformance test**, not a pixel ratio: over the Edge-case Corpus and a Reference Dataset file, every cluster's LineLayout x — where the tile raster draws it — equals the x of the same glyph in Monaco's DOM (`Range` rects) within `zoom × n / 128 + 0.05` CSS px, where `n` is the number of Monaco token spans before the glyph on its line, and the baseline is equal within 0.5 CSS px, at zoom 1 and non-integer zooms (0.8, 1.37, 2). The span term is the browser's, not Monaco's: Chrome rounds each inline fragment's width to a LayoutUnit (1/64 px), so the DOM x drifts from the sum of advances by at most 1/128 px per fragment boundary. Measured 2026-09-29 on a 171-column ASCII line: 1-, 5-, 20-character spans and a single span drift 1.33, 0.266, 0.008 and 0.008 px at the last column, at transform scale 1 and 2 alike. The GPU view does not emulate this rounding — that would couple the layout to Blink's LayoutUnit and to Monaco's span splitting; like VS Code's GPU renderer, it keeps one arithmetic layout. On a widget's visible width the drift stays under one device pixel for typical code.
- **Units** (task 3.1): world and Camera are in CSS px; every pass converts to clip space with one transform that takes a DPR uniform; tiles are rasterized at the raster scale (zoom × DPR) and drawn as quads in world units. The minimap quad samples only the uploaded rows, one minimap row per content line; the minimap tile size is a uniform, never a shader constant. Rendering tasks are verified with e2e at `deviceScaleFactor: 2` asserting pixels from screenshots, plus a one-off probe with console listeners and 1:1 captures — the half-size-on-DPR-2 defect of 3.1 was invisible in downscaled screenshots. Expected colours come from the rendering source constants, never hand-computed. The e2e checks include: crispness as the GPU view's horizontal gradient energy over Monaco's on the same region, ≥ 0.85 at zoom 1, DPR 2; overlap colours by Stack Order at both Detail Levels; and, from the per-frame draw counts, no frame with neither content tiles nor minimap quads (both appear together only during the crossfade).
- **Line window**: the uploader holds a widget's cells for the visible lines plus one screen's worth of margin above and below, from which its tiles are rasterized; when scroll moves outside the window, `DocumentResidency` rebuilds it within its drain budget (D7, D8). Pixels exist only for the visible area and a one-tile margin ring — never for all 2000 lines × 200 files.
- **Per-widget clipping** — in the fragment shader, against the widget body rectangle from `WidgetTable` (one instanced draw for all tile quads, no per-widget scissor).
- **Stacking order via the depth buffer**: each widget gets a unique depth from `StackOrder`. Pass 1 — opaque widget backgrounds/frames, writing depth; pass 2 — content: tiles when the Detail Level is "Text", minimap quads when it is "Minimap", depth test `LEQUAL` with no write. This way the content of a widget below doesn't show through the background of one above; since all widgets share one Detail Level, each frame draws one kind of content, except during the Detail Level crossfade, when both are blended over each widget's own background. Translucent backgrounds, shadows, and rounded corners with cutouts are not supported by this scheme.
- **Minimap** (Detail Level "Minimap"): the strip image is built on the CPU in the tokenization worker right after tokenization — a `Uint8Array` of palette indices (R8, 0 = background), one texel row per line of code, fixed width 256 texels (spike E: the whole Reference Dataset's minimap atlas is 26 MB R8), bounded height (long files are decimated). The texture is transferred to the main thread as a transferable and loaded into a shared minimap texture atlas through `DocumentResidency`'s budgeted drain (D7). The atlas is one R8 `TEXTURE_2D_ARRAY` with a 256 × 512 layer per Source File (~128 KiB, ~26 MB for 200 files); layers are assigned outside a frame from the `FilesDiscovered` subscription, which precedes every `FileContentChanged` of the folder; a file keeps its layer while it stays listed, growth re-creates the texture, and files beyond `MAX_ARRAY_TEXTURE_LAYERS` are logged. All minimaps are drawn in one instanced call, whose instances are rebuilt only when the atlas or the WidgetTable rows change; color is looked up in the shader from the palette, `NEAREST` filtering by index, no mipmaps (averaging indices is meaningless). At far zoom, a widget is a single quad sampling the file's visible slice. A naive RGBA-with-mipmaps variant was rejected: on the order of hundreds of MB for 200×2000 lines (a design-review estimate, not a measurement); "a rectangle per token run" was rejected: up to ~1M instances.
- The **file path** — in the header at Text and in a large font over the minimap — is drawn from label tiles: the raster workers draw it once per widget and raster scale; label tiles live in the tile pool and scale during gestures like Text Tiles. A raster job carries its canvas size, so a header or label comes back at its own size and takes a pool cell. Headers and labels never depend on the content: a widget without a line window gets a path-only source on its first visible frame, its header and label are requested and drawn whatever its content range, and it never counts as ready for Text or for time to sharp. Labels are laid out per widget when the settled zoom or the frame size changes and survive line-window replacements. (A path-only widget that skipped its header and label requests once left a Minimap view without labels and the FrameLoop idle.)
- **Detail Level transition** — the single Detail Level switches within one frame, with hysteresis (research risk #5), and the picture follows it as a crossfade of `DETAIL_FADE_MS` = 150 ms (user's decision, 2026-10-06, after looking at a prototype: the instant switch looked abrupt; it replaces "an instant switch; a crossfade was rejected"). The renderer keeps one text weight (1 = Text, 0 = Minimap) and steps it toward the current level each draw by the elapsed time (clamped to 50 ms; a reversal moves back from the current weight; it snaps at startup and after a context restore). While it is between 0 and 1 a frame draws both representations over each widget's opaque background: the minimap quads at alpha 1 − w, the content tiles at alpha w, the minimap labels at 1 − w, the headers at 1; the draw stage reports the fade as pending work so the FrameLoop keeps ticking. The earlier reason to reject a crossfade — blending two translucent representations breaks the stacking order of overlapping widgets — does not hold: backgrounds are opaque and write depth, content is drawn with `LEQUAL` and no depth write, so each widget's two representations blend only over its own background. Content tiles are drawn only where resident; the fade adds no tile requests. Zooming out, the scaled tiles stay until the switch to Minimap, whose textures are ready (spike E: Minimap frame GPU p99 1.09 ms, 8 switches with no empty frame; its zoom-sweep trace, re-derived with the corrected classifier — see D13 — has 1 dropped frame of 701, none partially presented). Zooming in, text cannot be ready ahead of time for every widget (a widget at the threshold scale is one 1 MiB tile, ~200 MiB for the dataset): when a zoom-in gesture starts at the Minimap level, the raster workers start on the tiles the threshold view will need — the widgets visible at the Text threshold zoom around the gesture's focus point, at that zoom's raster scale — and Board switches to Text only once the visible widgets' tiles are resident (D4); until then the Minimap stays, so no frame shows an empty widget, and the two representations appear together only during the crossfade (spec `code-widget-rendering` "Transition without flicker"). On a fast zoom-in the switch can lag the threshold by the raster time of the visible set (estimated ~0.1–0.2 s; user's decision, 2026-10-01, over keeping a threshold tile for all 200 widgets). H2 never crossed the threshold; the harness scenario "Zoom from "Fit all" to 4.0 and back" does.
- **Draw calls per frame**: 3–5. Culling — brute-force iteration over 200 AABBs, no spatial index: the cull stage walks the WidgetTable rows each frame and fills a reused map of visible line ranges for `DocumentResidency.visibleRangesChanged`. At Minimap the map is empty unless Board says Text is wanted, so minimap-only widgets get no line windows.
- **Context loss**: `webglcontextlost` is cancelled (`preventDefault`) and no GL call is made while the context is lost — draw returns the last metrics, uploads only record what they would upload. On `webglcontextrestored` the renderer re-creates every GPU resource (WidgetTable texture with all rows, passes, palette, minimap atlas, and TileResidency's tile pool, tile pass and job queue) and replays its inputs: file paths, minimap files, Detail Level, each file's latest line window, and the kept minimap bytes, re-uploaded a few per drain. TileResidency itself survives the loss with its state — Text wanted, the hidden body, the priority file, the gesture phase, the redraw callback — and re-creates only its GL resources, so no caller keeps a second copy of those inputs to replay (user's decision, 2026-10-06). Callers keep the same renderer object.

### D7. Tokenization

- There is a single source of color: the theme object, from which both `monaco.editor.defineTheme` and `ThemePalette` (`code-view/infrastructure/theme.ts`) are built — color matching by construction.
- The tokenizer is a **TextMate grammar** (TypeScript and TSX) run by `vscode-textmate` with the `vscode-oniguruma` WASM regex engine in a Web Worker. There is no tokenization of widget text on the main thread: that would contradict spec `performance-budget` "No background stalls". The `Tokenizer` port in `code-view/application` hides the implementation.
- Monaco (editing) uses the **same** grammar and the same scope-to-colour theme through a custom tokens provider, so a file's colours are identical in a widget and in the editor (spec `code-widget-rendering`); the editor tokenizes only the one file being edited.
- Why not Monarch (decided by the user after spike D, 2026-09-28): spike D proved Monaco's Monarch TypeScript grammar runs in a worker and matches Monaco byte for byte, but that grammar has no JSX rules and does not distinguish function identifiers, which spec `code-widget-rendering` "TypeScript syntax highlighting" requires. The spike D findings about the worker build (exports-map import form, the `editor.api.js` shim) no longer apply to the tokenizer; they still apply to how the editor loads Monaco.
- Spike D2 (task 2.9) settled the grammar and theme: `tm-grammars` `source.ts`/`source.tsx` and Dark Plus from `tm-themes`, converted from VS Code's `tokenColors` to `vscode-textmate`'s `IRawTheme.settings` (a plain cast silently yields only fallback colours). Zero worker ↔ Monaco colour mismatches over 55.7M characters; packed runs are `[line-relative offset, colour id]` pairs, ~460 KB per 2000-line file. The production build loads the WASM in the worker; the Vite dev-server WASM path was not measured.
- Cost (spike D2, production build): a cold 2000-line file takes ~375 ms, 12× Monarch; the whole dataset ~75 s in one worker. With a per-line rule-stack (`StateStack`) cache, the first visible 60-line window takes ~10.5 ms, re-tokenizing after a one-character edit ~0.6 ms (a full rescan 182 ms), a 100-line chunk ~18 ms. Hence the Tokenizer interface below is incremental and chunked, not whole-file.
- **Worker pool** (user's decision, 2026-09-29): the Tokenizer adapter runs a pool of workers (size from `navigator.hardwareConcurrency`, 4–6 on the reference machine, leaving cores to the main thread and the GPU process) so the cold dataset finishes in roughly 15–20 s (an estimate from ideal scaling; the harness measures it). Each file is pinned to one worker, so its rule-stack cache lives in one place.
- **DocumentResidency** (`code-view/application`) owns each Source File's path from text to GPU-ready data: text, Content Version, tokens, minimap bytes, the visible line range, and whether it is still unhighlighted. Its interface is small: `contentChanged(fileId, version, text)`, `visibleRangesChanged(ranges)` (from the FrameLoop after culling), `prioritize(fileId)` (from `EditingTransition`), and `drain(budget, uploader)`. It translates visible ranges and priority into the Tokenizer's ranked `wanted` line ranges. Ordering (priority, then visible, then the rest), staleness and the single-color fallback live only here. It is one folder module with one entry point: its internal parts (the priority queue, the Content Version ledger that drops stale results, the line-window planner, budget accounting) are implementation details, not imported from outside the folder and tested only through the four methods with the fake `Tokenizer` and a recording `GpuUploader`. Its rules:
  - A Content Version not newer than the current one is ignored. The tokenizer-result listener only runs O(1) staleness and contiguity checks and queues; all building happens in `drain`.
  - A file's line window is the hull of its visible ranges ± one screen; it is rebuilt only when the hull leaves it and never built for a file that is not visible. A prioritized file that is not visible asks for the whole file.
  - `wanted` is re-sent only when the ranking (priority, then visible in map order) or a range changes, with `[]` for files that left it.
  - `visibleRangesChanged` runs every frame: the caller may reuse and mutate its map, arrays and range objects, because only the hull is kept, as numbers per file. A call costs O(map entries + previously visible files) and allocates nothing unless a window is re-planned or the ranking changes; `drain` allocates nothing when there is no work.
  - The residency backlog in the Frame Sample is the number of visible files with unfinished window or recolour work plus queued minimaps, computed at the end of `drain`.
- Internal seam `Tokenizer`: the worker-pool adapter in production, a synchronous in-process fake in tests (two adapters). The theme and grammar are given once, when the adapter is constructed, never with each request. The adapter owns, per Source File, the current Content Version, the rule-stack cache and a resumable queue of line chunks (~100 lines); the cache is a live object inside the worker, which is why the interface speaks in content changes and line ranges, not whole-file jobs (user's decision, 2026-09-29, after the architecture review). `DocumentResidency` sends `contentChanged(fileId, contentVersion, text)` and `wanted(fileId, lineRanges)` in its priority order (priority, visible, the rest); the adapter tokenizes the wanted ranges first, resuming from the cached state before them, and can drop or reorder queued chunks between chunks, so no request blocks a worker for more than one chunk. A ranking replaces the previous one (first = most urgent), so `DocumentResidency` sends its whole ranking whenever it changes, and the `wanted` calls made in one task form one ranking. A cached line is reused only when its text and its entering rule stack are both equal, which makes a one-character edit about one grammar call. Responses are `(fileId, contentVersion, line range, Token Runs)`, plus the minimap bytes once a file is complete; results for one file arrive in order. A stale response is dropped inside `DocumentResidency`, before anything is queued for the GPU. Results (`Uint32Array` of Token Runs, `Uint8Array` of minimap data) are transferred as transferables, without copying.
- External seam `GpuUploader`, declared in `code-view/application`: it accepts line windows — cells (UTF-16 bounds and x offsets per LineLayout) with palette colour indexes, tied to a Content Version — and minimap bytes. Colour index 0 means "not highlighted yet", colour id + 1 a Theme Palette colour; whitespace-only clusters are not cells. The Theme Palette reaches rendering once, at construction; tokenizer results carry no palette. `rendering` implements it with WebGL; tile planning, the raster workers and the tile pool belong to that adapter (Text Tiles are rendering's concept, D6). Its per-frame main-thread work — posting raster jobs and uploading the tiles that came back — runs inside `drain`'s budget; a worker's message handler only queues the result. Tests use a recording fake. The whole path "text changed → uploads issued" is therefore testable with no worker and no GL.
- `drain` serves a prioritized file's visible line window and uploads that widget's tiles as they arrive regardless of the budget (bounded to one widget); everything else stays within the budget. It reads the clock after every unit of work (one window line or one upload) and resumes where it stopped on the next call. The priority ends once the file's highlighted window is uploaded.
- Until tokens are available, the widget is drawn in a single color (spec `code-widget-rendering`).

### D8. Frame cycle and work budget

- A single `FrameLoop` driven by `requestAnimationFrame`, running only while there are "dirty" changes or a gesture is in progress; it does not spin at rest. A Frame Stage reports whether it left work that needs another tick — the residency drain stopped on its budget, a tile was uploaded, an exit swap is held — and the FrameLoop requests one more tick when any stage did (user's decisions, 2026-10-02 and 2026-10-05). The stages that wait on tiles — the held exit swap (D2) and the deferred switch to Text (D4) — run before the drain in the tick order, so they see the new tiles on the next tick. Events outside a tick (input, a worker result, a timer, the layout store) invalidate the FrameLoop; the layout store's callback right after `restoreBoard` does, so the restore stage then sees the new `layoutVersion` (D5). Without this rule a held exit or a pending switch to Text stayed stuck whenever no further event arrived, and a line window that needs several drains stalled; a private keep-alive per waiting stage was rejected. It is a generic stage runner (`rendering/frame-loop.ts`): its interface is an ordered list of named **Frame Stages** plus the "dirty, pending work or gesture in progress" rule. It times every stage and, once per frame, hands one **Frame Sample** (stage times, Detail Level, visible widget count, residency backlog) to `FrameStats` through the type in `shared/frame`. `app` declares the stage list below in one place; each context contributes its stage through its public `index.ts`. A unit test with recording fake stages checks the order.
- Tick order: `GestureTargeting` turns accumulated input into intents → commands to board/editing → Camera and Detail Level → drain Board's dirty widget ids into `WidgetTable` → culling → `DocumentResidency.visibleRangesChanged` → `EditingTransition` applies its swap once the widget's tiles are current (D2) (Monaco container, widget visibility, priority file) and the pending gesture accumulated in GestureTargeting replays → `DocumentResidency.drain(budget, uploader)` (default 2 ms; line windows, tokens, minimaps; the remainder carries over, priority then visible first) → the renderer's tile drain under its own budget (default 2 ms: raster jobs posted, the prioritized widget's first, then visible widgets top-most first; returned tiles uploaded as they arrive, ≈0 ms each in H2) → draw. Tile work has its own budget in rendering rather than a share of DocumentResidency's (user's decision, 2026-10-04): it shares no queue with tokenization, and the prioritized widget reaches rendering as data from `EditingTransition` — the same file id `prioritize` receives.
- The same-frame swap on exiting editing and the budgeted drain do not conflict: the swap record and the prioritized widget's line window and tile uploads are the only work allowed outside the budgets, and both are bounded to one widget.
- Fast scrolling inside a widget: the line window has margin, and if the rebuild didn't finish in time, the frame draws the already-loaded window, missing lines are loaded in subsequent frames; a tile row that is not resident yet shows the widget background for those frames (counted as missing-tile frames). The harness includes a maximum-speed scroll scenario with a queue-depth metric.
- The hot input path has no per-event allocations: intents and commands take primitives, and there are no hot-path domain events (D5).
- Input: `wheel` on the canvas, non-passive, with `preventDefault` (pinch = `wheel` + `ctrlKey`); pointer events with `setPointerCapture`. Events accumulate and are applied once per frame.
- **Pinch follows the fingers** (user's decision, 2026-10-01): Chrome reports a touchpad pinch of scale s as ctrl+wheel events with Σ deltaY = −K·ln s, so each event zooms by `exp(−deltaY / K)` and a pinch of ×2 zooms by ×2. K is one constant in `shared/pinch.ts`, shared by the product and the harness: 142.6, measured by letting Chrome zoom a page that does not cancel the wheel (a CDP synthetic touchpad pinch ×2 gave Σ deltaY −98.8 at `visualViewport.scale` 2.000; the −100·ln s first assumed here was wrong). A real trackpad could not be measured the same way (Chrome left `visualViewport.scale` at 1.0); the user confirmed by feel on the reference MacBook that the text stays under the fingers with K = 142.6 (2026-10-02). One event's zoom step is clamped to e^±0.1, so a Ctrl + mouse-wheel notch zooms by about 10% instead of jumping. The vertical slice's `exp(−deltaY · 0.002)` zoomed a ×2 pinch by about ×1.22.
- **GestureTargeting** (`interaction`) is the one module that decides what a gesture does. It picks the target when a gesture starts, using Board's hit-test, the Detail Level and whether an Editing Session is active, and keeps that target until the gesture ends, including the OS momentum phase: a scroll that reaches a widget's content edge stays on that widget; a plain wheel over the editor goes to Monaco; pan or zoom on the canvas while editing ends the session and carries on as a pending gesture; drag and resize of the active widget are refused. Its interface is raw events in, per-frame intents out, so every routing scenario in the specs is a unit test over a recorded event sequence, with no browser. Its rules:
  - It has no timers: one reused intents object is returned per `takeIntents(now)`, and the 150 ms wheel-idle end of a gesture is detected by the take or by the next event. A change of the Ctrl/Meta modifier starts a new gesture.
  - A wheel scrolls a widget only at Text, over its body, when its content does not fit; otherwise it pans. Scrolling another widget while editing does not end the session — it is not a canvas pan.
  - Pointer: header → drag, right/bottom band and corner → resize (absolute position and size; Board clamps), body → click; all three bring the widget to the front at pointer-down. While Space is held any pointer-down pans, without bringing anything to the front.
  - While editing: pointer-down on empty canvas ends the session with reason "pan" and a pending pan; on another widget it ends the session with reason "outside" and does nothing else; on the active widget's header or edges it does nothing.
  - An end-of-editing request is peeked and applied by the input stage before the take, so during a held exit the gesture keeps accumulating inside GestureTargeting and the swap tick replays it (D2).
  - Shift+1 (Fit all) and Shift+0 (Zoom to 100%) are matched by `code`, with Shift alone and not on key repeat; the toolbar buttons go through the same requests. During an Editing Session they end it with reason "zoom", and the camera change applies after the held exit swap. Keys typed in Monaco, in a form control or on a button never reach GestureTargeting; toolbar buttons cancel the `mousedown` default so they never keep the focus (a focused button swallowed shortcuts and Space). Every key that does reach it invalidates the FrameLoop.

### D9. Monaco

- One instance per application, files are switched with `setModel()`; models are created on entering editing and disposed on exit (we don't keep 200 models).
- The DOM container over the canvas is placed once on entering editing; the camera and the active widget's geometry stay stationary until exit (spec `code-editing` "Stationary editor"). Plain wheel input over the container is handled by Monaco; a Ctrl/Meta wheel (a pinch) over it is forwarded to GestureTargeting and its propagation stopped — otherwise a pinch over the editor never reaches the canvas and Chrome zooms the page. Any other input on the canvas ends the session.
- Opening a file in the editor takes bounded steps: the Monaco model is created one task before the editor opens it, and opening does not lay the editor out — placing the container calls `layout(size, true)`, one postponed render (a model switch had rendered synchronously twice in one task). A switch to a never-opened 2000-line file costs about 3.7 ms for `createModel`, 2–3 ms for `setModel` and ≈4 ms of Monaco plus 2–3 ms of Chrome for the first render, each in its own task.
- Monaco's configuration is minimal: no minimap, overview ruler, word wrap, code lens, diagnostics, or semantic tokens, and none of the decorations the GPU view does not draw — bracket pair colours, bracket matching, occurrence and selection highlights, whitespace in selections, Unicode highlighting, links, colour decorators, sticky scroll (all on by default in Monaco 0.57). Turning them off cut the "Typing" scenario's typing frames from a median of 4.9 to 3.6 ms and its paste from 5.5 to 2.8 ms (`perf:stages`, 10 runs each, 2026-10-03).
- **Metric alignment**: Monaco always receives the base `fontSize`/`lineHeight` from `shared/font.ts`; its container is scaled to the camera zoom with CSS `transform: scale(zoom)` (origin top-left, no `will-change`). Monaco's layout is then the zoom-1 Text Metrics layout — the same one the GPU view scales — at any zoom and for any font, including fallback fonts whose advances do not scale linearly with font size. Measured 2026-09-29 in Chrome at DPR 2: emoji advances are 20/21/22/24 px at font sizes 16/17.6/20/24 (Menlo and CJK scale linearly); against the zoom-1 layout × zoom, Monaco with `fontSize` × zoom deviated up to 16.7 CSS px at zoom 2, with CSS `zoom` up to 16 px, with `transform` ≤ 0.03 px at zoom 0.8/1.1/1.37/2; clicks landed on the right column in 37 of 37 clusters and drag selection was exact in every mode; text under the transform is rasterized at the final scale, as sharp as a native font size. The camera is not snapped on entering editing: the earlier snap existed only because Monaco rounds a fractional `lineHeight`, and the base `lineHeight` is whole. The horizontal step and the baseline come from Text Metrics (D6), which Monaco's DOM shares by construction; Monaco is never probed for metrics. Spike C matched the frame before and after entry within ~1.5 CSS px at zoom 0.8/1/1.37/2 with Monaco-probed metrics; the product's first attempt to probe Monaco (`getScrolledVisiblePosition` deltas over a probe model) produced zero and inflated advances for code points outside the laid-out viewport and a guessed baseline, and was replaced by Text Metrics (2026-09-29). Acceptance is D6's conformance test at zoom 1 and non-integer zooms.
- **Loading Monaco** (spikes B/C/D, Monaco 0.57): import through the `exports` map without `esm/vs/` (`monaco-editor/editor/editor.api.js`), never the package's full entry — it registers the TypeScript language service; internal APIs moved (`model.tokenization.*`); the editor needs `self.MonacoEnvironment.getWorker` with its editor worker.
- **Task budget** (user's decision, 2026-09-29): spike C saw 1–2 main-thread tasks of 9.9–11.8 ms per action (typing, paste of 500 lines, undo, model switch; earlier runs up to 21.5 ms), 0–2 dropped frames and 32–40 ms from input to the next paint, but could not separate Monaco from its own harness. Accepted for now; the performance harness measures Monaco in the product (tasks 4.x, 11.8), and a miss there is the AGENTS.md stop point again. Measured in the product on 2026-10-03 (`perf:stages`, 10 runs): typing ≤ 7.1 ms, paste of 500 lines ≤ 5.5 ms, model switch 5.0–8.6 ms, and the frame after undoing that paste 5.8–10.6 ms (up to 13.0 ms before the minimal configuration above). That frame is Chrome rendering Monaco's DOM for the ~40 visible lines it replaces — style 2.3–2.5, layout ≈ 2.9, HTML parsing ≈ 1.9 and paint 1.6–2.1 ms — plus ≈ 3 ms of Monaco's own script; Monaco already merges adjacent tokens of one colour. Decision (user's, 2026-10-03): an edit that replaces most of the editor's visible lines may take one task of up to 16 ms and miss one frame (spec `performance-budget` "Frame budget"); the harness measures it in the scenario "Large edit in the editor" with its own ceiling in `perf/budgets.json`, while typing and model switching keep the 8 ms limit. Decision (user's, 2026-10-04): a line break (Enter) may take one task of up to 12 ms and miss one frame — in the headed full run of 2026-10-04 its frame took 7.8–10.0 ms (2–3 ms of script, the rest Chrome repainting the editor's DOM as every visible line below the cursor moves), over 8 ms in three of five runs; the harness measures it in "Line break in the editor" with its own ceiling, and "Typing" types no line break. Decision (user's, 2026-10-06): typing may take one task of up to 10 ms and miss two frames per run of "Typing" (16 keystrokes and two editor switches). In the headed full runs of 2026-10-06 its tasks took 5.4–8.6 ms and its runs missed [1,1,0,5,3] and [1,1,1,3,1] frames on both the current code and c701147; the keystroke frame is Monaco's input handling and render (median 3–6 ms keydown to commit) plus Chrome painting its DOM, while the FrameLoop does not tick on a keystroke. Disabling bracket colorization (11 vs 14 missed frames over 15 runs), `editContext: false` (worse) and `disableLayerHinting` (noise) brought no gain. Decision (user's, 2026-10-07): the Typing task ceiling is 12 ms — in the headed full runs of 2026-10-06 the worst Typing task on one and the same code ranged from 7.2 to 11.2 ms between runs (A/B 19-39-31 vs 19-49-44, Monaco's first-keystroke handling), so a 10 ms ceiling failed by chance (two noisy runs that day reached 31–35 ms).
- **EditingTransition** (`editing/application`) owns the whole enter/exit sequence, so the "one frame" invariant lives in one module. It depends only on narrow views of Board's read model and of workspace's `readForEditing`/`applyDraft`. `begin(widgetId, contentPoint)`: `readForEditing` with conflict check, asynchronously; when the read resolves it captures the editor placement, opens the Monaco model and its scaled container through the `EditorHost` port, puts the cursor at `LineLayout.positionAt` of the hit-test's body-local point, and wakes the FrameLoop. An `end` while the read is pending cancels it. `end()`: `applyDraft` only if there are unpublished edits, `DocumentResidency.prioritize`, model disposal. Edits are recorded from `EditorHost.onChange`, not by comparing strings: Monaco's model normalizes line breaks (a lone CR becomes the model's end-of-line), so `getValue()` of an untouched CR-only file differs from the Source File text (measured 2026-10-02), and a string comparison turned every exit from such a file into an edit. Autosave: the composition root owns one timer, armed from `onChange` and re-armed from `autosaveDueAt()`; `autosave(now)` publishes the Draft through `applyDraft` when `AutosavePolicy` is due. An exit always waits until the widget's view is covered (user's decisions 2026-10-04/05, replacing "a session that published nothing swaps at once", which showed a blink on Escape): every visible part of the body at the Content Scroll the exit hands back from Monaco is covered by resident tiles of the latest Content Version — the one the session published, at an autosave or at the exit, or the opened one if it published nothing — at any raster scale (the draw set's coverage rule, D6), judged on a residency plan made at that scroll. Sharpness is not part of the hold: waiting for exact-scale tiles held the exit forever at non-integer zooms; a scaled tile sharpens afterwards like after any zoom. A raster error releases the hold. `discard()` ends the session without publishing (a Save Conflict resolved to the disk version, D12). Any widget's body at Text can enter editing. `begin` on another widget during a session ends it with reason "another-widget" (edits published) and remembers the request; during a held exit of another widget it remembers the request, a newer one replacing it; applying the exit swap starts the remembered request. This is what makes "Double click on another widget" work: GestureTargeting ends the session on the double click's first pointer-down, so the double click reaches `begin` during the held exit. A `begin` on the same widget or during a pending read is refused. An edited file is saved with the model's normalized line endings, as VS Code does (user's decision, 2026-10-02). The swap is applied by `EditingTransition` itself, atomically, in the FrameLoop's editing stage — in the first tick in which the widget's tiles are current for the new Content Version (D2): it hides or shows the widget's GPU representation and sets the priority file through a narrow GPU-view port (the renderer in production, a fake in tests), and places or removes the Monaco container through `EditorHost`; it also tells input wiring whether input is held (a held exit). The pending gesture is not part of the swap: it keeps accumulating inside GestureTargeting (D8) and the swap tick replays it (user's decision, 2026-10-06; the swap record's former `pendingGesture` field was never read). `EditorHost` has two adapters: Monaco in production, a fake in tests, so every exit reason in the spec (Escape, click outside, pan, pinch, double click on another widget) is tested without Monaco or WebGL.
- **Scroll across the swap** (user's decision 2026-10-04): the widget's Content Scroll is the one scroll position. On entering, `begin` sets Monaco's `scrollTop` to the widget's Content Scroll before the enter swap, so the visible lines do not move and the cursor lands on the clicked line. On exiting, `end` writes Monaco's `scrollTop` back to the widget's Content Scroll through the Board's scroll command (clamped like any scroll), so the GPU view shows the lines the user last saw in the editor; the exit swap's tiles are requested for that scroll.

### D10. Linting and quality gates

A single `pnpm check` command (the agent must run it before committing; the pre-commit hook repeats it on changed files):

|---|---|---|

### D12. Storage

- The folder handle is stored in IndexedDB; on startup, `queryPermission`, and if needed, `requestPermission` on click (Chrome 122+ offers a persistent permission).
- Folder identity is a workspace concern: workspace matches a newly picked handle against saved handles with `isSameEntry` and assigns a stable `WorkspaceFolderId`; a folder seen for the first time gets `crypto.randomUUID()`.
- Each context owns its IndexedDB database (workspace: `code-canvas-workspace` with the folder handles and state; board: `code-canvas-board` with the layouts), so no context upgrades another's schema.
- Layout (Board: widgets + camera) is stored in IndexedDB keyed by `WorkspaceFolderId`. Board counts layout changes with a revision counter (an increment, no callback on the hot path), and a 1 s periodic check saves a changed layout, so a change is saved no later than 1 s after it happens. Restoring is one step: board's infrastructure, subscribed to `FilesDiscovered`, loads the saved layout and passes it to the application-layer `restoreBoard(folderId, files, savedLayout, viewport)`, which runs the pure `reconcile` policy (D4), so no widget is placed before the layout is known. `restoreBoard` takes a loaded layout because the store is infrastructure with no port (D3, the seam rule below). A load overtaken by a newer folder is ignored, and the open folder's layout is saved before switching. Rejected: a `.code-canvas.json` file in the folder — that writes into someone else's repository.
- Seams only where two adapters exist: `DirectoryReader`/`FileWriter` (File System Access + the harness mock), `Tokenizer` (worker pool + sync fake), `EditorHost` (Monaco + fake), `GpuUploader` (WebGL + recording fake). The IndexedDB stores for the folder handle and the layout have one production adapter each; they are tested against an in-memory IndexedDB (`fake-indexeddb`) rather than behind a port. The e2e and harness directory mocks are real OPFS directories, because the adapter stores the handle in IndexedDB and a plain mock object cannot be stored; each call creates a uniquely named directory, so two steps in one page never share a folder id and its saved layout.
- Writing a file: immediately before the write, the file is re-read and hashed; if the hash doesn't match the known File Revision → `SaveConflict` (spec `workspace-storage`). `lastModified` + size are used only to avoid re-reading files when scanning the folder. Writes are serialized per file. The re-read catches an external write made between `readForEditing` and the Draft's write; one made between the re-read and our own write cannot be caught — File System Access has no compare-and-swap.
- Write errors: a failed write publishes `DraftWriteFailed`; workspace keeps the failed files and re-writes them on `retryFailedWrites()`, and the app shows a `role="alert"` notice while a write is failing and retries through one timer (1 s, doubling to 30 s). A conflict is not retried.
- Save Conflicts: `resolveConflict(fileId, "disk" | "mine")` runs through the per-file write queue. "disk" re-reads the file and drops its unsaved and failed state; during an Editing Session of that file the session is discarded first, so no late autosave overwrites the disk. "mine" writes the in-memory text without the revision check, and the session continues. The notice lists conflicting files in arrival order, names each through `textContent`, disables its buttons while resolving, stays if a resolution fails, and is cleared by `FilesDiscovered`.

### D14. Security

- File paths and names are rendered to the DOM only via `textContent`; `innerHTML` in `src/` is forbidden by the linter (`no-restricted-properties`).
- The `window.__perf` bridge and the File System Access mock exist only in the build with `VITE_PERF_HARNESS=1`; a test builds the regular bundle and verifies the absence of the bridge strings and mock adapters; the regular build's composition root does not import the mock.
- The code font is the system font named in `shared/font.ts` or a file from the bundle; there are no external downloads; the page's CSP forbids third-party script and font sources; workers are module scripts from the bundle (no `blob:` workers).
- The tokenizer workers receive only the file's text and the raster workers only its cells; the grammar and theme are static, nothing from file content is ever executed.

### D13. Performance harness (`perf/`)

A separate Node tool in the same repository (spec `performance-harness`). It is built right after the spikes and before the main features, so that every rendering task is checked by it from day one.

```
perf/
  harness/
    cli.ts            commands: run [--quick] [--scenario <name>], self-test, baseline:update
    preflight.ts      environment validity
    driver.ts         feeding gestures through CDP
    trace.ts          trace recording and frame parsing
    metrics.ts        collecting app metrics through the bridge
    report.ts         JSON + Markdown, comparison with the baseline
    coverage.ts       matching scenarios against the performance-budget spec
  scenarios/          declarative scenarios (*.ts, schema validated with zod)
  budgets.json        thresholds and allowed deviations from the baseline
  baseline.json       the baseline (committed)
  acceptance/         manual acceptance traces (committed, .json.gz)
  results/            run artifacts (in .gitignore)
```

- **Browser launch**: Playwright + system Chrome stable (`channel: 'chrome'`), a visible window covering the whole built-in display, no flags touching vsync/frame rate. Headed runs open a context without viewport emulation in a maximized window: Playwright's default 1280 × 720 at DPR 1 rendered a quarter of the display's pixels, and Chrome scaled CDP wheel deltas by the screen's DPR 2 against it, so every gesture ran twice as far (measured 2026-10-01).
- **Preflight**: headless detection (`navigator.webdriver` is not enough — user agent and CDP `Browser.getVersion` are checked), flags from CDP `Browser.getBrowserCommandLine`, idle rate — 2 s of rAF intervals on an empty page (threshold ≥ 115 Hz), Low Power Mode — `pmset -g`. Machine model, display refresh rate, DPR and the power source (`pmset -g batt`) go into the report; battery power does not abort a run (user's decision, 2026-10-04).
- **Feeding gestures**: preferably CDP `Input.synthesizeScrollGesture` / `Input.synthesizePinchGesture` — they go through the browser's input and compositor pipeline, like a real trackpad; for drag/resize — `Input.dispatchMouseEvent`, for typing — `Input.dispatchKeyEvent` (a line break is a key-down with text `"\r"`, as a real Enter; a double click is two press/release pairs). A paste is a `ClipboardEvent("paste")` with a `DataTransfer`, dispatched through `Runtime.evaluate` on the focused element, never the system clipboard; an evaluation that reports `exceptionDetails` fails the run. CDP `Input.insertText` was rejected: Monaco takes it as typing (1,442 ms for 500 lines). Scenario points avoid the toolbar, and a pan starts over a header or a gap between widgets, because at Text a wheel over a body scrolls that widget; drag starts on a header, resize in the grab band (D4), and a manipulation run ends with the layout it started from. Which CDP gestures produce, on macOS, the same DOM events as a trackpad (pinch → `wheel` + `ctrlKey`) is checked in spike A; the fallback is `Input.dispatchMouseEvent` of type `mouseWheel` with the Ctrl modifier, paced by a high-resolution Node timer. The driver uses the fallback. **Honest gestures** (spike H2): events go out at their planned times without awaiting each acknowledgement — awaiting serialized a gesture at ~45 ms per event, 5× its plan; a pinch of scale s is sent as ctrl+wheel with Σ deltaY = −K·ln s, the product's own constant (D8), as Chrome reports a touchpad pinch. A run is an invalid measurement (exit code 2) when its gesture took more than 1.5× its planned time, its final camera differs from the planned one (scale by more than 2%, position by more than 2% of the planned displacement or 2 world px), or — for a zoom — the camera's recorded scale range misses the planned extremes by more than 2%, since a round trip that ends where it started proves nothing on its own: a slower or shorter gesture than planned makes the frame numbers look better than they are.
- **Frame classification**: a CDP `Tracing` trace with DevTools timeline categories; parsing uses the same trace engine as the DevTools Performance panel, published as an npm package (`@paulirish/trace_engine`; its availability and API are checked in spike A). If it can't be used — a homegrown parser of frame events, cross-checked against the DevTools panel on the same trace (the spec's "Artifacts" requirement). There is **one** trace classifier, in `perf/harness/trace.ts`, seeded from spike C's `spikes/c/trace-analysis.mjs`. Dropped and partially presented frames are counted from the trace engine's frame model (`FramesHandler`, its `dropped` and `isPartial` frames) — the model that draws the DevTools Performance panel's Frames track, which is what the spec's criterion names. Raw `PipelineReporter` states (paired by the trace engine; `STATE_PRESENTED_ALL`, `STATE_PRESENTED_PARTIAL`, `STATE_DROPPED`) are kept in the report as a diagnostic and still define presentation times for intervals: on the same headed traces (2026-10-03) they counted a drop at every keystroke of "Typing" and ~600 partial frames during "Pan during initial load", all with `affects_smoothness: false`, where the frame model showed 0–1 dropped and 0 partial (user's decision, 2026-10-03; this answers spike A's open question whether the pairing matches DevTools — it does not). The tracing categories must include `cc` and `disabled-by-default-devtools.timeline.frame`; a parse failure, zero frames or zero main-thread tasks is an invalid measurement (exit code 2), never a 0. Frames and intervals are counted only inside the **interaction window**: from the first to the last renderer `EventDispatch` (category `devtools.timeline`) of a `wheel`, mouse or `keydown` event the driver sent, plus 100 ms for the frames that present the last input; task metrics use the whole trace, and a trace without input (the noise floor) is judged whole. Counting the whole trace turned idle time into "intervals over 12.5 ms": a pan run had 4–8 of them with no dropped frame (2026-10-01). Inside the window, a gap between two presented frames that holds only `STATE_NO_UPDATE_DESIRED` frames (DevTools' idle frames) is idle time, not an interval; a gap with no frame record (a missed display-link tick) or with a frame of any other state still counts (user's decision, 2026-10-03). A gap whose frames all carry `affects_smoothness: false` in their `PipelineReporter` record is not an interval either (user's decision, 2026-10-04): in the headed "Typing" traces of 2026-10-03 the double click that switches the editor's file arrived 1–2 ms before a vsync, its input handling (~3 ms) and main frame (3–4.5 ms) missed that vsync, and Chrome reported the frame as a `BACKFILL` drop not affecting smoothness — the screen was still before the click, so the user sees the response one refresh later, not a stutter, and the frame model did not count it as dropped; that gap was the only interval over 12.5 ms in four of five runs. The application-task limit still catches the expensive keystroke (Enter: one 9 ms main frame, mostly the editor's paint). **Wake-up frames** (user's decision, 2026-10-04): a frame whose begin-frame has `subtype: "MISSED"` (the renderer's `Scheduler::BeginImplFrame` args; a frame-model frame is matched by its start time, which equals the begin-frame's `frame_time_us` — the model labels that frame with the next sequence number, so sequence numbers do not match) is excluded from the dropped and partially presented counts and from interval gaps, and is never an interval endpoint: in the 2026-10-04 06:10 run a keystroke at 1206.3 ms woke the display, the missed begin-frame for 1200.1 was presented, and the next frame came at 1216.1, so measuring from the missed frame's time reported a 16 ms interval that no one saw. Viz sends such a begin-frame when a client starts requesting frames again (`NeedsBeginFrames` after the display link stopped), with the frame time of the last, already-past refresh and a deadline a few milliseconds away. In the 2026-10-04 headed "Typing" run the second editor switch came after 600 ms of still screen with no display-link tick; the double click at 2606 ms woke the display, Viz sent a missed begin-frame for 2600.0 with its deadline at 2608.7, and the frame was dropped with `affects_smoothness: true` (the app's frame loop then ran a few frames, which Chrome treats as main-thread animation) while the main thread had no task over 0.3 ms; the frame model counted it as partially presented in four of five runs. During a continuous gesture the client never stops requesting frames, so no frame there is a missed one (0 missed begin-frames in the 2026-10-03 pan, zoom and drag traces; in "Typing" every keystroke after a pause starts with one). The DevTools panel still shows these frames; a manual trace is compared against the harness with them set aside. Between keystrokes of "Typing" the compositor reports one such frame and stops requesting frames until the next input (seen in every gap over 20 ms of five stages traces), so without the rule each keystroke was one interval over 12.5 ms. Spike E's first classifier matched event names and traced without `cc`, so its "0 dropped" could not have been anything else.
- **Frame statistics**: one module defines the percentile (nearest rank), the long-interval count and "unavailable" for an empty sample; `FrameStats` (overlay) and the harness both use it through the bridge. The spikes had six percentile copies with two definitions.
- **Measurement hygiene** (spikes B–E): measure on a production build served by `vite preview`, never the dev server; load dataset text raw (`?raw` import or file read — the Vite dev server returns transpiled JavaScript for a `.ts` URL); compare colours as resolved hex, not colour ids; accept no number without opening its capture (screenshots, traces).
- **App bridge**: a build with the `VITE_PERF_HARNESS=1` flag exposes `window.__perf` — `FrameStats` by stage, GPU time via `EXT_disjoint_timer_query_webgl2` (if available), synthetic-load control for the self-test, state-preparation commands (open the reference dataset without a dialog via the File System Access mock, set the camera). In a regular build the bridge is stripped at build time. The bridge type is the single file imported by both the application (`src/performance/bridge.ts`) and the harness; the rest of `src/` is off-limits to the harness (the boundaries rule). The bridge is installed only after the app is ready (the "Open folder" button stays disabled until its listener is attached, and e2e tests wait for the enabled button, never sleep); its `openFolder` resolves once every Source File has a widget, and `beginEditing(path)` resolves once that widget's Editing Session is visible (Text required, 10 s limit, otherwise invalid `editing-unavailable`).
- **Settled runs**: the bridge's settle state is true when the FrameLoop is idle (or a synthetic load is active, which invalidates every tick by design), there is no zoom gesture, time to sharp is not running, no raster job is in flight and none failed, every visible text widget has exact tiles at Text, the residency backlog is 0, no switch to Text is pending, and no Source File's current Content Version still lacks its minimap (the backlog alone reads 0 between two tokenizer results). The harness waits for two consecutive settled polls, one animation frame apart, before every run and after its gesture (60 s, otherwise invalid `app-not-settled` with the last state). Stage metrics come from the snapshot right after the trace, time to sharp from one after the wait.
- **Initial load**: a scenario with `initialLoad` reloads the page, reopens the Reference Dataset and sets the camera in every run, warm-ups included, and skips the settle wait; a run whose tokenization had already finished at the gesture start is invalid (`load-finished-before-gesture`), as is one with Reference Dataset files missing.
- **Scenario scale**: setup scales are given for a device pixel ratio and converted to the page's, so the device px per line — which decides the Detail Level — is the same headless at DPR 1 and on the reference display at DPR 2; a setup can approach its scale from another one first, for the hysteresis. "Worst-case text density" runs at 0.23 at DPR 2 (9.2 device px per line, just above the Text threshold), approached from 0.3, and ends with a short pinch that measures time to sharp.
- **Scenario metrics**: the switch lag is the largest time from the first frame that wants Text (`textSwitchPending` in the Frame Sample) to the first Text frame — 0 for a switch in the same tick, nothing recorded when the zoom falls back below the threshold; maximum-speed scroll is 24,000 CSS px/s (≈200 px per wheel event at 120 Hz) down then back up, so runs never stick at the content end; the residency backlog's maximum is in every report.
- **Noise floor**: before the scenarios — in full mode on the app page before the folder opens, a visible 16 × 16 fixed canvas recoloured every animation frame, for the same duration and with the same set of trace categories; the result goes into the report and into the comparison against thresholds (spec `performance-budget` "Noise floor"). The floor is classified by the same frame classifier as the scenarios, and an invalid classification makes the run invalid, never a zero floor. (The first floor drew into a canvas not attached to the document, which presents no frames, and fed raw trace events to the verdict as if classified: every stored floor was 0.) A frame drop is a rare random event, so a 60 s floor of 0 does not mean a zero rate. The self-test's empty-scene case therefore does two things:
  - it allows the one-sided 95% Poisson upper bound of the floor's dropped + partially presented rate, scaled to each run's duration (0 observed per minute → 3 per minute);
  - it fails only if a majority of the measured runs exceed that allowance.

  Frame-budget scenarios use the same rule for both floor-relative metrics — dropped + partially presented frames, and intervals longer than 12.5 ms, each against the upper bound of its own floor rate — while absolute budgets (the 8 ms application task, baseline regressions) are judged on the worst run (user's decision, 2026-10-02). The case that decided it: in the 2026-10-02 full run, one of five pan runs had a single 14.9 ms interval 33 ms into the gesture, where macOS delivered no display-link callback (no `CVDisplayLinkCallback` between 32.9 and 47.0 ms, so no BeginFrame was issued); the app had requested that frame and its tick took 0.3 ms. The other runs had none, and a zoom run had a similar 12.0 ms gap. At that session's rate the worst-run rule fails a scenario on such an event roughly once in six full runs; a hitch the app causes in every run still fails.
- **Task attribution**: a main-thread task is counted as an application task if its stack contains code from the app bundle (including Monaco) or it was spawned by the app's event handlers, timers, rAF, or worker messages; everything else is a browser task.
- **Repetitions**: 1 warm-up run + 5 measured runs by default (`budgets.json`); floor-relative frame metrics fail only in a majority of runs (see "Noise floor"), absolute budgets on the worst run; the report shows the worst run and the spread. A scenario gets its own application-task ceiling and extra missed frames per run (`scenarioOverrides` in `budgets.json`) only where the spec grants an exception — today "Large edit in the editor" (2026-10-03), "Line break in the editor" (2026-10-04) and "Typing" (2026-10-06).
- **Coverage**: `coverage.ts` reads the `#### Scenario:` headings of the "Frame budget" and "No background stalls" requirements from `openspec/specs/performance-budget/spec.md` (before the change is archived — from `openspec/changes/code-canvas/specs/`) and requires a scenario with the same name.
- **Output for agents**: stdout carries the verdict and a table (scenario × key metrics × delta to the baseline); everything else goes into `perf/results/<time>/`. Exit codes: 0 — passed, 1 — budget violation or regression, 2 — the measurement is invalid (preflight).
- `FrameStats` is the shared source for the metrics overlay and the harness; it is fed only by the FrameLoop's Frame Sample (D8), so `performance` imports no context. The overlay (Shift+M) cycles hidden → compact → detailed → hidden (user's decision, 2026-10-07, for demos): compact shows FPS, frame interval p50/p99, dropped frames (the long-interval rule), the worst tick of the last 2 s, visible/total widgets and the Detail Level with its text weight; detailed adds per-stage p95/max, tile pool slots and MiB, raster jobs in flight and posted per second, drawn and fallback tiles, time to sharp, tokenizer backlog and camera zoom. The draw stage writes these as plain numbers into the reused Frame Sample (O(1), no allocation); every aggregate and the text are computed only on the overlay timer. It refreshes on a 500 ms timer only while visible, and a sample taken after the loop was idle records no interval — idle gaps would dominate its p99.
- **Stage-timing mode** (`pnpm perf:stages`): the same scenarios in any Chrome, including headless, only frame stages and application tasks, exit code 3 for "not a frame measurement" — for agent iteration. A run without Frame Samples is invalid there, except in an editor-only scenario (it edits a file and has only typing, paste, key and wait steps), where Monaco draws and the FrameLoop may never tick; keying the exception on the edited file alone would let a broken editing bridge pass. Stage mode runs headless at 1280 × 720 and DPR 1, the full run maximized at DPR 2, so a change whose cost depends on the viewport is confirmed headed (the tile pool that never settled, D6, showed only headed).
- **Baseline**: `pnpm perf:baseline` requires interactive confirmation in a TTY; without a TTY — an error, no changes. The pre-commit and pull-request guard that rejected changes to `perf/baseline.json` and `perf/budgets.json` without a human marker was removed (user's decision, 2026-10-04): it only made the human set an environment variable on their own commits; that only a human edits those files stays a process rule in AGENTS.md.
- Running from an agent sandbox may fail to open a visible Chrome window; in that case the user runs the full run (`! pnpm perf`) and hands the agent the report path.

## Risks / Trade-offs

- Chrome/macOS stays at 60 Hz without a trigger (research, risk #1, T3 single) → spike A on day one; if confirmed — a programmatic trigger (fullscreen/resize) and a description in the reference environment; if unattainable — revisit the acceptance criterion before development begins.
- Glyph shift on the frame of entering/exiting editing (Monaco's fractional metrics, fonts that do not scale linearly) → Monaco at the base font size under a CSS transform and the Text Metrics conformance test (D6, D9); there's no frame-by-frame synchronization during panning — the camera is stationary in the editor.
- Monaco itself exceeds 8 ms on typing, model switching, or IME → minimal configuration (D9), typing/paste/model-switch scenarios in the harness; if the budget is unattainable — a stop point with the user, not a silent exclusion from the criterion.
- Text is sharp only at its raster scale; during a zoom gesture it is scaled → exact-scale re-raster in the raster workers after the gesture, old tiles kept until the replacements land; time to sharp in the harness (D6).
- TextMate tokenization (Oniguruma regexes) is 12× slower than Monarch on a cold file (spike D2) → a worker pool, visible windows first, a per-line rule-stack cache for edits, and chunks the adapter can reorder (D7); the main thread never tokenizes widget text.
- A Detail Level transition switches every widget in the same frame → the Minimap is always ready; Text is prepared from the start of a zoom-in gesture and the switch to Text waits for it; the switch is one uniform followed by a 150 ms crossfade (D6); spike E measured the worst case for the Minimap.
- A re-raster burst after a zoom gesture or on entering Text → raster workers off the main thread, budgeted uploads, old tiles kept until the replacements land, the switch to Text deferred until text is ready (D6); harness scenarios "Zoom from "Fit all" to 4.0 and back" and "Worst-case text density".
- Text Tiles hold pixels, not glyphs: memory grows with the visible area (H2: 36 MiB for a 1200 × 720 view) → a tile pool with pool cells for short tiles, LRU, growth outside the frame up to a cap and never a shrink, tile memory in the Frame Sample (D6).
- Not measured in spike H2, carried to the product harness: smooth sub-tile scroll, time to sharp, the exit-editing hold, the deferred switch to Text, missing-tile frames during a zoom-out.
- A flood of worker responses after opening a folder → `DocumentResidency`'s budgeted drain with visible files first and stale versions dropped (D7); scenario "Pan during initial load".
- One concept split across modules hides bugs in the coordination → single owners: `EditingTransition` for entering/exiting, Board for Detail Level and hit-test, LineLayout for text → rows and cells, `DocumentResidency` for text-to-GPU, `GestureTargeting` for input routing, FrameLoop (with the stage list in `app`) for tick order (D4, D7–D9).
- An absolute zero of dropped frames is unattainable due to OS noise and trace recording → the criterion is relative to the noise floor of the same session (spec `performance-budget`).
- Integrating components that were only verified individually → a vertical slice right after the spikes, before the harness and the contexts (tasks, group 3).
- DDD adds layers and files → technical modules with no domain layer (D1), projections for the hot path (D5); the linter enforces boundaries so agents can't cut corners.
- The harness's synthetic gestures don't behave like a real trackpad → the final criterion is manual acceptance with real gestures (spec `performance-budget`); the harness is a regression check.
- The harness itself may lie (false "green" results) → a self-test with artificial CPU and GPU load, cross-checking the frame count against the DevTools panel on the same trace, a weekly manual trackpad trace for comparison.
- An agent "fixes" a regression by updating the baseline → the update requires interactive human confirmation.
- A full run requires a visible window, the agent waits on a human → stage-timing mode for agent iteration, a full run at least twice a day.
- The 800-line limit invites splitting into small, highly coupled files → `max-lines-per-function` and `complexity` matter more than the file-size limit; review looks at module cohesion, not just size.
