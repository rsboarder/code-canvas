# Spike H2 — frames under pan and zoom: WebGL glyph atlas vs. Canvas2D tiles

## Method

`spikes/h2/` renders 200 Reference Dataset widgets in a 10 × 20 grid. Each
widget is 760 CSS px wide with a 900 CSS-pixel clipped body. The scene uses
`LineLayout` and `TextMetrics` for grapheme x positions and the E threshold of
9 device pixels for switching from flat rectangles to Text. The density scenario
uses the computed zoom 0.225, the lowest Text zoom for the 20 px line height at DPR 2. The page
selects one renderer with `?renderer=atlas`, `?renderer=tiles-main`, or
`?renderer=tiles-worker`.

Renderer A reuses Spike H's verified atlas packing, padded/clamped UV records,
glyph shader, and alpha upload at discrete 8/12/16/24/32/48/64/96 CSS px sizes.
Atlas glyph vertices carry their widget body clip rectangle; the fragment shader
discards samples outside that rectangle. Validation also counts text-mask pixels
in the computed inter-widget gaps and requires `validation-text-outside-widget`
to remain at zero.
The next raster size is prepared in bounded 2 ms frame slices and switched only
after a gesture once its texture is complete; it emits one WebGL glyph draw call
per visible widget. Preparation frames are counted separately from atlas builds,
texture creations, and instance-buffer rebuilds. If the zoom invariant fails,
the cell runtime reports the named counter that moved.

Per D7, widget instance buffers are never built synchronously inside a frame.
`AtlasRenderer` computes each widget's glyph count from its text content once,
at construction, giving every `widget.index` a fixed, stable vertex-offset slot
in one persistent GPU buffer sized up front (`ensureAtlasInstanceCapacity`).
Each frame queues widgets within an 800 world-px margin around the viewport
(visible widgets first) and spends up to a measured 2 ms building/uploading
queued widgets (`atlasWidgetBuildMs` median/p99/max, `atlasUploadMs`
median/p99); a widget's own data is written directly into a pre-sized
`Float32Array` (no intermediate JS array). Uploading is one `bufferSubData`
call into that widget's own slot — no other widget's data moves, so there is
no full re-concat-and-reupload of the whole visible set. A visible widget
whose buffer is not ready yet draws without text for that frame
(`atlasMissingTextFrames`). Because no widget's slot ever moves, there is no
"full instance-buffer rebuild" left to violate D6/D7 during a gesture;
`atlasInstanceBufferRebuilds`/`atlasGestureViolations` are structurally always
zero now, not just observed to be zero.
Renderers B and C reuse Spike H's Canvas2D `fillText` cell raster helper and use
fixed 512 × 512 device-pixel
Canvas2D tiles and a 3072 × 3072 RGBA tile atlas (36 slots, 36 MiB pixel
budget). B rasterizes on the main thread within a 4 ms per-frame budget. C
rasterizes in an inline `OffscreenCanvas` worker and transfers `ImageBitmap`
tiles; the main thread only uploads and composites. During a zoom gesture both
tile renderers keep the old raster zoom and do camera-only work. The harness
sends an explicit `endGesture` signal after the planned events; only then are
replacement tiles created. Old ready tiles remain scaled on screen until all
replacement tiles upload. `timeToSharpMs` ends at the last replacement upload.
This avoids a settle timer firing between slowed wheel events. The `time`
stage waits for tile coverage to reach the expected area right after
`endGesture()` (mirroring the validate stage) before reading metrics for a
run; reading them immediately after `endGesture()` always raced the
replacement upload, so `timeToSharpMs` reported "not measured" in every timed
zoom run.
`tilesRasterizedDuringGesture` is the invariant counter and must remain zero for
zoom; pan may rasterize newly exposed tiles. Worker ImageBitmap uploads are
drained in bounded frame work instead of running synchronously in message
handlers.

Validation loads the approved `webgl-lint` 1.11.4 dependency only for the
validation stage. It configures the `GMAN_debug_helper` extension with a high
draw-call limit and `throwOnError: true`; the initial load and post-setup rest
frame, including the pixel check, are linted. The harness disables the linter
before dispatching the gesture, because gesture checks use counters and do not
need per-call linting. Timing pages do not load it. The trace stage uses the
pinned Perfetto binary described below, not an npm package, so trace processing
remains outside the timing run.

`measure.ts` is staged and runs renderers in the required order B `tiles-main`,
C `tiles-worker`, A `atlas`. `--stage smoke` checks only B × pan. `--stage
validate` runs all twelve cells (pan, zoom, density, scroll × three
renderers) with validation-only WebGL lint, a
`preserveDrawingBuffer` pixel check in the same draw task, named invariant
failures, and a rest PNG. `--stage time` reads only validation-pass cells and
uses a warm-up plus three measured gestures with rAF, Long Animation Frame,
Long Task, and disjoint-safe GPU timer-query metrics. It does not start tracing
or WebGL lint, and each cell has its own 30 s cap. Results are written
atomically to one JSON file per cell; `--resume` skips an existing cell.

`--stage trace` records one confirmatory zoom pinch per renderer as raw
protobuf, then invokes the pinned Perfetto `trace_processor_shell` v58.2
binary after SHA-256 verification. Raw traces are never parsed with
`JSON.parse`. `--stage summary` reads only cell files, writes `summary.json`
and the table below, and exits 0 only when every validate and time cell is
present and passing (exit 2 for missing cells, exit 1 for failures).

The existing `--record <renderer> <scenario>` screencast mode remains
available. It writes an `alignment` object in `frames.json`; it compares
text-mask centroids before and after the first atlas-size switch and fails
above 0.5 device pixels. Each sample includes the wheel-handler p99 and the
per-frame JS p99 reported by the page. The PNG sanity check requires at least
100 pixels that differ from both the product and widget backgrounds. Validation
failure cells retain the validation object, runtime metrics, and the expected
versus actual value for the failing check. The validate stage exits 0 when all
requested cells pass, 1 for a failure or timeout, and 2 for missing cells.

The corrected headed Chrome run is lead-only. Values not present in the lead's
`spikes/h2/results/summary.json` are written as **not measured**, never inferred.
The `--record atlas zoom` capture also writes an `alignment` object in
`frames.json`; it compares text-mask centroids in the frames before and after
the first atlas-size switch and fails above 0.5 device pixels.

### Scroll scenario (round 10)

A fourth scenario, `scroll`, exercises in-widget scrolling for all three
renderers. Camera is `[0, 0, 1]`; the plan is a plain (non-ctrl) wheel at
`(380, 400)` — inside widget 0's body, away from its edges — scrolling down
at 3000 CSS px/s for 1 s, a 0.5 s wait, then back up for 1 s (the existing
`scroll` step kind and `Input.dispatchMouseEvent`/`mouseWheel` plumbing in
`perf/scenarios/schema.ts` and `perf/harness/driver.ts` already supported
this; only `measure-shared.ts`'s scenario table and the page itself needed
scroll support). `GestureTargeting` is simplified for the spike: each wheel
event re-hit-tests the pointer against widget bodies (`main.ts`
`widgetBodyAt`) instead of locking a target for the gesture's lifetime —
equivalent here since the plan keeps the pointer stationary. Because the
planned 3000 px vastly exceeds a widget's clamped scroll range (content is
capped at 80 lines, the body fits ~45, so the max offset is well under 1000
px), both legs of the scroll saturate their clamp and the scenario
deterministically returns the widget to offset 0 — the validate stage checks
`getState().scrollOffset` against 0 within one line height
(`validation-scroll-offset-mismatch`), on top of the existing gesture-speed,
glyph/tile-area and no-text-outside-widget checks (unaffected, since by
gesture end the visible content is back to the unscrolled baseline).

For the atlas, scroll is a per-widget uniform the shader subtracts from the
glyph y position (see the instancing section below): a widget's instance
buffer holds all of its lines up front, so scrolling touches no GPU buffer at
all. For tiles, the on-screen tile grid (tileX, tileY) stays fixed and a
per-widget `scrollBucket` (whole tile-row counts) shifts which source lines
are painted into a slot; a bucket change is a new cache key and falls into
the same "rasterize what's missing within budget" path pan already uses for
newly exposed tiles — this is a deliberate simplification (tiles scroll in
whole-tile-row increments, not sub-tile-smoothly) that keeps `emptyTileFrames`
as the honest cost of a scroll instead of adding a second, scroll-scoped
fallback-tile mechanism alongside the existing zoom-settle one.

### Atlas density fix (round 10)

The atlas glyph path is now instanced: one static unit quad
(`SceneGpu`'s `quadCornerBuffer`, divisor 0) drawn via
`drawArraysInstanced(TRIANGLE_STRIP, 0, 4, instanceCount)`, with a 16-byte,
4-float per-glyph instance record (`model.ts` `ATLAS_INSTANCE_BYTES`): local x
within the widget's content, line row, atlas slot index, and palette index —
no world coordinates, no per-glyph UV or size (D6 "Glyph instance"). Per-slot
geometry (local offset + quad size) and UV rect live in a small data texture
(`H2Atlas.slotTexture`, one per raster size) the vertex shader reads with
`texelFetch`, indexed by atlas slot (D6: "a slot table in a uniform/data
texture") — down from 264 bytes/glyph (6 non-instanced vertices × 44 bytes)
to 16 bytes/glyph, reported as `atlasInstanceBytes`.

Widget position, scroll offset and clip rect are per-draw-call uniforms, not
per-instance data, because each widget now has **its own** `WebGLBuffer`
(`SceneGpu.createAtlasWidgetBuffer`) instead of a shared one — this is the
chosen fix for "never `bufferSubData` into a range the GPU may still read":
a shared buffer meant every widget's build/upload had to serialize behind
whatever the *other* 199 widgets' draw calls were doing on the GPU timeline
(the measured 28–43 ms/frame `CommandBuffer::Flush` cost); per-widget buffers
confine that hazard to a widget's own prior draw, and each buffer is written
exactly once with `bufferData` (never `bufferSubData`), which is itself an
orphaning-style store re-specification if a rebuild ever did happen. Per-widget
buffers were chosen over orphaning/double-buffering the one shared buffer
because the access pattern is already per-widget partial updates, not a
whole-buffer rewrite each frame — double-buffering the whole scene would mean
duplicating every widget's data into both copies. Because a widget's instance
record no longer depends on raster size (atlas slot indices are stable across
raster sizes — `AtlasRenderer` reuses the same `clusters` order for every
`createAtlasPreparation` call, round 9's fix), a raster-size switch only ever
swaps the active texture and slot table, never any widget's buffer — a
widget's own buffer is rebuilt only when its line window moves (round 11).
Draw-call count per frame (`atlasDrawCallCount`) stays one per visible widget
with a built window, same as before.

Live validation of this round caught a real GL state bug: `drawAtlasWidget`
enabled attributes 1..4 every call and `endAtlasInstancedDraw` only reset
their divisors, never disabled them, so they stayed enabled in the **default**
VAO (shared with the rect/texture passes); once a widget's buffer was deleted
(`reset()`), the next unrelated `drawArrays` call failed WebGL validation
("no buffer is bound to enabled attribute"). Fixed with a **VAO per widget**
(`SceneGpu.createAtlasWidgetBuffer` now also creates and configures one),
rather than a manual disable in `endAtlasInstancedDraw`: it isolates the
instanced attribute state from the default VAO entirely, and as a side
effect removes the per-widget-per-frame attribute setup, since it now happens
once at build time. Uniform locations (`SceneGpu.atlasUniforms`) are looked
up once at program creation instead of once per frame/per widget, and the
palette is uploaded once (it never changes), not reallocated every frame.

### Time-to-sharp root cause (round 10, third attempt)

Root cause: `timeToSharpMs` was never a read-timing race — `waitForTileCoverage`
polls `coveredTileArea`, which `tiles.ts` `draw()` computes from the **fallback**
tile set while a replacement is in flight (`coverageTiles = fallback.length > 0
? fallback : tiles`). The `zoom` scenario's net scale factor is `2 × 0.25 × 2 =
1`, so the camera returns close to its starting position, and the stale
fallback tiles (rastered before the gesture) already cover close to
`expectedTileArea` on the very first poll — long before
`TileRenderer.replacementReadyAt` is ever set. The two earlier fixes both
adjusted *when* metrics were read against this same proxy condition, which
cannot work: the proxy is satisfied by data from *before* the replacement
starts, not by the replacement finishing. The fix (`measure-stages.ts`
`waitForTimeToSharp`) polls the real signal — `getMetrics().timeToSharpMs`
becoming a number — instead of tile coverage, for the `zoom` scenario
specifically (`pan`/`density` never trigger a raster-zoom settle, so
`timeToSharpMs` staying "not measured" there is expected, not a bug).
Independently of whether this closes the race, the validate stage now fails a
tiles `zoom` cell outright when `timeToSharpMs` is not a number
(`validation-time-to-sharp-missing`), so a regression can never again pass
silently.

### Round 11: product-sized scene and an atlas line window

The lead's live run found `model.ts` cutting every file to 80 lines
(`source.split("\n").slice(0, 80)`): the product shows whole Reference
Dataset files, up to 2000 lines, so every H2 number up to round 10 came from
a scene several times lighter than the product, and the `scroll` scenario
saturated its clamp in ~0.3 s instead of exercising real scrolling. The cap
is removed; `createWidgets` keeps the dataset's **longest file by line count**
deterministically pinned to widget 0 (ties broken by path, the existing sort
order), not whichever file happens to sort first — widget 0 (the scroll
scenario's target, pointer at `(380, 400)`) must hold well over 3000 px of
content for the scenario to exercise scrolling rather than clamping. On this
worktree's fixtures (`pnpm fixtures`), that file is
`fixtures/reference-dataset/group-00/widget-000.tsx`, 2000 lines (2001 after
`.split("\n")`, the trailing empty line from its final newline) — content
height 2001 × 20 = 40,020 px, max scroll 39,120 px, comfortably over the plan's
3000 px. The scroll scenario's plan is now 3000 px down, a 0.5 s wait, 1500 px up (lead's
change, `measure-shared.ts`); `SCROLL_EXPECTED_FINAL_OFFSET = 1500` is the
exact arithmetic result since the longest file is now long enough that 3000 px
down no longer saturates the clamp.

With full files (up to 2000 lines), round 10's "build a widget's whole
content once" no longer fits: a single widget's content could be millions of
glyphs. The atlas now implements D7's **line window**: a widget's instance
buffer holds only the lines in `[visible.firstLine − margin, visible.lastLine
+ margin)`, clamped to the file — `atlas.ts`'s chosen margin is **one
screen's worth of lines on each side** (`VISIBLE_LINE_COUNT`, ≈45 lines at the
default line height and body height), per D6's "the visible lines plus one
screen's worth of margin above and below"; a widget's window is therefore at
most ~3 screens of lines regardless of file length. `AtlasRenderer` tracks
each widget's currently drawable window (`activeWindows`) separately from
what the current scroll offset actually needs
(`model.ts` `visibleLineRange`/`windowCoversRange`): when the visible lines are
no longer covered, a rebuild is enqueued through the same bounded (≤ 2 ms/frame)
build queue as before, computed fresh at build time (not at enqueue time, so a
widget queued a few frames ago rebuilds for wherever scroll actually is by the
time its turn comes), into a **new** buffer + VAO; the **old** window keeps
being drawn until the new one is ready (D8 "fast scrolling: draw the
already-loaded window, missing lines load in subsequent frames"), then the old
buffer/VAO is freed. A frame where the currently visible lines aren't covered
by the active window counts toward `atlasMissingTextFrames` (text is on screen,
just stale, until the swap). New metrics: `atlasWindowRebuilds` (count of
window replacements, excluding each widget's first build) and
`atlasWindowBuildMsP99` (p99 build+upload time of just those replacements).
`expectedSceneCounts` (`pure.ts`) is now scroll-aware (an optional
`scrollOffsets` parameter, keyed by each widget's position like `Widget.index`):
expected glyphs follow the widget's actual scrolled visible line range, not
always lines 0..45, which also closes a latent bug from round 10 — the atlas
used to report its *whole* built window's glyph count as "drawn", which could
exceed the always-lines-0..45 expectation once per-widget windows held more
than the strictly visible lines; the atlas now counts only glyphs within the
intersection of the active window and the currently visible range.

Tiles need no change in approach: a widget's tile grid
(`ceil(WIDGET_WIDTH/size) × ceil(BODY_HEIGHT/size)`) is sized from the fixed
body/viewport geometry, not file length, and `tileContentOriginY`'s
`scrollBucket` only changes which lines are read into a tile, never how many
tiles exist — tile memory and raster counts stay bounded with full files by
construction, confirmed by reading `tiles.ts`, not by a code change. The
existing whole-tile-row scroll simplification (round 10: tiles scroll in
whole `size`-px row increments, not sub-tile-smoothly) is unchanged and still
applies with full files.

## Cost fields and trace evidence

For A, `atlasSizeSwitches`, `atlasBuilds`, `atlasTextureCreations`,
`atlasInstanceBufferRebuilds`, `atlasInstanceBufferPartialUpdates`,
`atlasGestureViolations`, `atlasPreparationMsMedian`,
`atlasPreparationMsP99`, `atlasPreparationFrames`, `atlasBuildMs`, and
`atlasMemoryBytes` are reported, along with
`atlasBuildsDuringGesture`, `atlasTextureCreationsDuringGesture`,
`atlasInstanceBufferRebuildsDuringGesture`, and
`atlasPreparationFramesDuringGesture`. Preparation is the bounded per-frame work used
to finish a target raster size before the post-gesture swap; the pan and pinch
rows keep it separate. `atlasWidgetBuildMsMedian`/`P99`/`Max` report the
bounded per-widget instance-buffer build cost and `atlasUploadMsMedian`/`P99`
the per-widget `bufferSubData` cost, both over every widget built during the
run; `atlasMissingTextFrames` counts frames where a visible widget's buffer
was not ready yet (tiles' `emptyTileFrames` equivalent).
The glyph-cluster set (`spikes/h/renderer.ts` `computeClusterSet`) depends
only on widget text content, not raster size, so `AtlasRenderer` computes it
once in its constructor and passes it into every `createAtlasPreparation`
call; re-deriving it per raster size (one `flatMap`/`Set` over all 200
widgets per call) was the real cost behind the atlas's remaining ~60 ms long
frames, invisible to `atlasPreparationMs` because only `step()` was timed.
`createAtlasPreparation`'s own canvas allocation/`getContext`/font setup is
now timed too and folds into `atlasPreparationMsMedian`/`P99`; its own max is
reported separately as `atlasPreparationCreateMsMax`. `rasterizeAtlas` and
other spike H callers are unaffected: the cluster set is an optional
parameter, defaulted to the same computation as before.
The page also reports JS frame p50 and p99; the pan and pinch rows keep those
measurements separate. For B and C, `tilesRasterized` and `tilesUploaded` are
separate counts, alongside raster median and p99, upload median,
`emptyTileFrames`, `timeToSharpMs`, and `tileMemoryBytes`. C additionally records
worker raster time in the raster fields and the combined ImageBitmap transfer plus
upload median as `imageBitmapTransferUploadMsMedian`. The trace row supplies
presented, partially presented, dropped, p99 interval, long-interval count,
longest application task, and the JS frame p99.
`residentTileGlyphs` is the sum of glyphs in the currently resident ready tiles,
including tile area outside the viewport; it is intentionally not the expected
on-screen glyph count.

All cost numbers are **not measured** until the lead runs the headed harness.
`--stage trace` runs the query from a file with `-q` (v58.2 has no `--csv`
flag; its default output is already CSV with a quoted header). Chrome reports
each physically displayed frame twice under the same
`frame_reporter.display_trace_id` — once as its own `frame_sequence`'s
`STATE_PRESENTED_ALL`, and again later as a carry-over
`STATE_PRESENTED_PARTIAL` contribution folded into the next `frame_sequence`
(same `display_trace_id`, later `ts`) — so counting rows directly double
counts every presented frame (measured: 928/928/32 raw ALL/PARTIAL/DROPPED
rows on `atlas-zoom.pftrace` is 961 real frames, not 1888). A
`STATE_DROPPED` frame has no `display_trace_id` (NULL), so grouping by
`display_trace_id` alone collapses every dropped frame into one NULL-keyed
group; group those by `frame_sequence` instead. The query used by
`--stage trace`:

```sql
WITH frame_events AS (
  SELECT
    ts,
    dur,
    COALESCE(
      EXTRACT_ARG(arg_set_id, 'frame_reporter.state'),
      EXTRACT_ARG(arg_set_id, 'chrome_frame_reporter.state')
    ) AS state,
    COALESCE(
      EXTRACT_ARG(arg_set_id, 'frame_reporter.frame_sequence'),
      EXTRACT_ARG(arg_set_id, 'chrome_frame_reporter.frame_sequence')
    ) AS frame_sequence,
    COALESCE(
      EXTRACT_ARG(arg_set_id, 'frame_reporter.display_trace_id'),
      EXTRACT_ARG(arg_set_id, 'chrome_frame_reporter.display_trace_id')
    ) AS display_trace_id
  FROM slice
  WHERE name = 'PipelineReporter' AND category GLOB '*cc*' AND depth = 0
),
frames AS (
  SELECT
    COALESCE(CAST(display_trace_id AS TEXT), 'seq-' || CAST(frame_sequence AS TEXT)) AS frame_key,
    MAX(CASE WHEN state = 'STATE_DROPPED' THEN 1 ELSE 0 END) AS any_dropped,
    MAX(CASE WHEN state = 'STATE_PRESENTED_ALL' THEN 1 ELSE 0 END) AS any_all
  FROM frame_events
  GROUP BY frame_key
),
main_tasks AS (
  SELECT MAX(dur) AS longest_main_task_ns
  FROM slice
  WHERE category GLOB '*toplevel*' OR category GLOB '*devtools.timeline*'
)
SELECT
  SUM(CASE WHEN any_dropped = 0 AND any_all = 1 THEN 1 ELSE 0 END) AS presented_all,
  SUM(CASE WHEN any_dropped = 0 AND any_all = 0 THEN 1 ELSE 0 END) AS presented_partial,
  SUM(CASE WHEN any_dropped = 1 THEN 1 ELSE 0 END) AS dropped,
  (SELECT longest_main_task_ns FROM main_tasks) AS longest_main_task_ns
FROM frames;
```

Measured frame counts (deduplicated), zoom scenario, from the three traces
already in `results/trace/`:

| Renderer | Presented (all) | Presented (partial) | Dropped | Longest main task |
|---|---:|---:|---:|---:|
| atlas | 928 | 1 | 32 | 86.5 ms |
| tiles-main | 961 | 1 | 0 | 29.2 ms |
| tiles-worker | 961 | 1 | 0 | 29.1 ms |

The "partial" count of 1 in each trace is a trace-window boundary artifact
(the first or last frame in the capture window, unpaired because its
counterpart falls outside the window), not a real partially-presented frame.

The pinned tool is downloaded only on the lead machine to
`spikes/h2/results/tools/` from Perfetto v58.2 mac-arm64 and checked against
`d29864d1ba3b36855527bb1b0ca3aa7f703cdce338b9680bb922c5c151b358fa`.

## Reproduction

1. Run `pnpm fixtures`.
2. On the reference machine, run `pnpm exec tsx spikes/h2/measure.ts --stage smoke`
   with visible Chrome, DPR 2, the built-in 120 Hz display, and no frame-rate
   or vsync flags.
3. Run `--stage validate`, inspect all twelve PNGs, then run `--stage time
   --resume` and `--stage trace`.
4. Run `--stage summary`; inspect the three `--record` captures if atlas
   alignment needs visual confirmation before drawing a performance conclusion.

Expected rough wall-clock estimates on the lead machine are smoke 15 s,
validate 1 min, time 5.5 min, trace 75 s, and summary under 1 s. These are
planning estimates, not measurements.

## Interpretation

**Verdict (human, 2026-10-01): Canvas2D tiles rasterized in a worker.** On
the 80-line scene it was the only variant within the frame budget in pan, zoom
and density (JS frame p99 ≤ 4.4 ms, GPU p99 ≤ 1 ms, no long animation frames).
On the full-size scene it holds the budget in pan, density and in-widget
scroll (JS frame p99 ≤ 3.3 ms, 0 dropped). The atlas needed a fix in every
round and crashed on the full-size scene.

- The atlas has the lowest per-frame cost under pan and zoom and about a tenth
  of the memory, but its cost grows with the number of visible glyphs and it
  misses the budget at worst-case density. A fix (compact per-glyph instances,
  no uploads into an in-use buffer) is plausible but unmeasured.
- Main-thread tiles fit, but spend up to 6.2 ms of JS per frame, too close to
  the 8.33 ms budget.
- Colour emoji are not required (user's decision, 2026-10-01).

Open for the product: smooth (sub-tile) in-widget scroll, time-to-sharp after
zoom, typing (all not measured), tile memory (38 MB), and the frames with
missing tiles (1–2 per run).
