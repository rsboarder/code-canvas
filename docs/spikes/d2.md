# Spike D2 — TextMate TypeScript/TSX tokenization in a Web Worker

## Question

Can `vscode-textmate` with `vscode-oniguruma` tokenize TypeScript and TSX in a
Web Worker, emit packed token runs and an R8 minimap, and provide Monaco with
the same grammar and theme colors? The reference comparison is Spike D's
Monarch result: approximately 31 ms per 2000-line file and 5.5 s for the
200-file dataset.

## Reference Chrome result (primary evidence)

The lead ran the built spike in headed Chrome 154 on the reference Mac (DPR 1)
against 200 generated files of 2000 lines each. These are the primary numbers;
the Node measurements below are only offline lower bounds.

| Measurement | Median | P95 | Max | Scope |
| --- | ---: | ---: | ---: | --- |
| Cold worker tokenization | 375.5 ms | 394.2 ms | 448.5 ms | one 2000-line file, 200 files |
| Warm worker tokenization | 372.9 ms | 392.3 ms | 392.3 ms | 20-file subset |
| Cold first visible window | 10.5 ms | 11.2 ms | 11.2 ms | lines 0–60, 20 files |
| Edit at line 10, incremental | 0.6 ms | 0.8 ms | 0.8 ms | 20 files |
| Edit at line 10, full rescan | 1.9 ms | 2.1 ms | 2.1 ms | 20 files |
| Edit at line 1000, incremental | 0.6 ms | 0.7 ms | 0.7 ms | 20 files |
| Edit at line 1000, full rescan | 181.9 ms | 190.3 ms | 190.3 ms | 20 files |
| 100-line chunk | 18.2 ms | 19.6 ms | 23.2 ms | 400 chunks |

The cold dataset pass took **75.4 s** for 200 files / 400,000 lines. The warm
20-file pass took **7.43 s**. Cold is approximately **12.1×** Spike D per file
and **13.6×** the full-dataset comparison, both beyond the requested 3×
threshold.

The incremental cache result is materially different: the benign one-character
edit converged after a median of two lines in all 20/20 files, including the
line-1000 edit. This is within the 100 ms post-edit target, but it does not
measure an edit that changes a multiline rule stack.

The lead result also reported zero worker/Monaco color mismatches across
55,740,464 compared characters. The tokenized-reference guard passed:
2,610,800 default-foreground characters out of 51,280,064 non-whitespace
characters. Packed runs were 459,760 bytes/file and 91,952,000 bytes for the
dataset; each 256×512 R8 minimap was 131,072 bytes. Transferable receive time
was approximately 0 ms.

The stored lead JSON predates the final exact-offset JSX sample check, so its
old `syntaxSamples.jsxTag` field must not be used as the final JSX evidence.
The lead must rerun once after this fix and record the new per-token worker ↔

## Method

The page loads the 200 Reference Dataset files through Vite's raw-text glob.
The worker is created with Vite's module-worker form:

```ts
new Worker(new URL("./tokenizer.worker.ts", import.meta.url), { type: "module" })
```

The worker loads `source.ts`, `source.tsx`, Dark Plus, and `onig.wasm`, carries
the TextMate rule stack across lines, packs each line as
`[line-relative startOffset, foregroundColorId]` pairs, and transfers the runs,
line offsets, and R8 minimap. Monaco uses an encoded provider backed by the
same grammar and converted theme.

`incremental.ts` caches the `StateStack` entering each line. It measures the
first visible window, resumes from the cached state after an edit, measures a
full-rescan baseline, and reports 100-line chunk timings. The browser harness
streams progress and writes partial progress before the final guard checks.

## JSX discrepancy: cause and fix

The first stored sample reported `Widget` as `#DCDCAA`, the same as
`renderWidget`, while the screenshot showed the actual component tag in teal.
The discrepancy was in the sample probe, not in the worker tokenizer: it used
`SAMPLE_FILE.indexOf("Widget")`, which found the `Widget` substring inside
`renderWidget` before reaching `<Widget`.

The probe now resolves every sample by an exact marker and line/column offset.
The parity table covers all requested token kinds:

- component tag: `<Widget`
- intrinsic tag: `<div`
- attribute: `className=`
- function identifier: `renderWidget`
- function call: `renderWidget(`
- method call: `plainIdentifier.trim`
- type annotation: `plainIdentifier: string`

For each token it records the worker hex color, Monaco hex color, and a match
flag. The guard also fails if any of these sample comparisons mismatch. An
offline exact-offset diagnostic confirms the component tag is `#4EC9B0`, the
function identifier is `#DCDCAA`, the plain identifier is `#9CDCFE`, the
attribute is `#9CDCFE`, the method call is `#DCDCAA`, and `string` is
`#4EC9B0`. These are Node checks using the same grammar/theme; the browser
parity table remains pending the lead rerun.

The other correctness fix is in the shared theme constructor. VS Code theme
JSON uses `tokenColors`, while `vscode-textmate` expects `IRawTheme.settings`.
The constructor now converts the theme explicitly and includes the editor
foreground/background. The color map has 20 entries after conversion; the
previous cast silently produced only fallback colors.

## Design impact — no decision made here

The cold result is a D7 stop-point candidate. Two design options remain open:

1. **Worker pool:** parallelize cold file tokenization. This is only an
   estimate, not a measured result: ideal scaling would put 75.4 s at about
   37.7 s with two workers or 9.4 s with eight workers. Real scaling,
   contention, and the useful pool size are unmeasured.
2. **Accept approximately one minute of background highlighting:** show text
   immediately, progressively highlight visible/ready widgets, and let the
   single worker finish in the background. This preserves the current
   correctness path but accepts delayed full highlighting.

Both options retain the per-line cache and bounded chunks for post-edit
responsiveness. This spike does not choose between them and does not edit
`design.md`.
